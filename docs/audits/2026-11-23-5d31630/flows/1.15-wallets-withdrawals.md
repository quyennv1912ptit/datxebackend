## 4. Mock Top-Up Security & Production Gating (Requirement #6)

- **Production safety**: All 3 controllers (`MockWalletController`, `DriverMockTopUpController`, `CustomerMockTopUpController`) require **both** `@Profile("dev", "test", "demo")` **and** `@ConditionalOnProperty(name = ["wallet.mock-topup-enabled"], havingValue = "true")`.
  - `docker-compose.production.yml:6` defaults `SPRING_PROFILES_ACTIVE=production`, and `application.properties:85` defaults `wallet.mock-topup-enabled=false`.
  - Even if `WALLET_MOCK_TOPUP_ENABLED=true` were mistakenly set in `production` or `prod`, Spring **will not register** any of the 3 controllers, and `WalletQueryController#overview` / `DriverWalletController#creditStatus` both check `activeProfiles.any { it in setOf("dev","test","demo") }` before advertising `mockTopUpEnabled = true` (`CustomerWalletEndpointsTests.kt:25-37`).
- **Role & replay guards (in dev/test/demo)**:
  - `DriverMockTopUpController` (`ROLE_DRIVER`) and `CustomerMockTopUpController` (`ROLE_CUSTOMER`) derive target ID exclusively from `@CurrentUser` (`actor.id`), restrict wallet type (`CREDIT` for driver, `CUSTOMER` for customer), bound amount to `1..50_000_000`, and deduplicate retries via `driver_mock_topups` / `customer_mock_topups` (`V20`/`V21`).
  - `MockWalletController` (`ROLE_ADMIN`) intentionally treats each call as a fresh top-up without idempotency (`docs/WALLET_MODULE.md:84`).
- **Operational note**: Never deploy `SPRING_PROFILES_ACTIVE=demo` to a real-money production environment, as `application-demo.properties` sets `wallet.mock-topup-enabled=true` and allows self-service mock top-ups.

## 6. New Confirmed Findings (Task 1.15)

### `F-007` — Withdrawal Create & Admin Approve Lack Server-Side Bank Account Validation and Bank Snapshot
- **Category**: Business Logic / Payout Integrity & Audit Trail
- **Task ID**: `1.15` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/payment/service/WithdrawalService.kt:26-61`
- **Actor / Entrypoint**: `DRIVER` via `POST /api/driver/withdrawals`; `ADMIN` via `POST /api/admin/withdrawals/{id}/review` (`APPROVE`)
- **Preconditions**: Driver has `CASH` balance `>= amount` and blank/null `bank_name` or `bank_account_number` (or modifies bank details after creating a `PENDING` request).
- **Expected Behavior** *(source: `docs/WALLET_MODULE.md:182-190`)*: A driver must have valid `bankName` and `bankAccountNumber` before creating a withdrawal request, and an admin must not be able to approve a withdrawal lacking bank details (and payout audit should record which bank account was paid).
- **Actual Behavior**:
  1. `WithdrawalService#create` (`WithdrawalService.kt:27-39`) locks `drivers(driverId)` but never checks `driver.bankName.isNullOrBlank() || driver.bankAccountNumber.isNullOrBlank()`, accepting withdrawal creation with no bank info if called directly via API.
  2. `WithdrawalService#review(APPROVE)` (`WithdrawalService.kt:42-61`) never loads or validates the driver's bank info before marking `SUCCESS`.
  3. `withdrawal_requests` (`V18`, `V22`) stores no `bank_name` / `bank_account_number` snapshot; `adminList` joins live `drivers.bank_name`/`bank_account_number`, so if the driver updates or clears bank details via `PUT /api/driver/profile/identity` while `PENDING` (or after `SUCCESS`), the admin queue and historical records silently show the mutated bank details.
- **Reproduction (Fake Data)**:
  1. Driver `7` (`bankName = null, bankAccountNumber = null`, `CASH = 100,000`) calls `POST /api/driver/withdrawals` with `{"amount": 50000}` and `Idempotency-Key: w-1` → succeeds (`200 OK`, `PENDING`).
  2. Admin calls `POST /api/admin/withdrawals/{id}/review` with `{"action": "APPROVE"}` → succeeds (`200 OK`, `SUCCESS`) despite missing bank account.
- **Root Cause**: Bank account validation was implemented only in the mobile/admin UI (`docs/WALLET_MODULE.md:182,190`), not enforced in `WithdrawalService`, and `withdrawal_requests` lacks snapshot columns (acknowledged as a limitation in `docs/PAYMENT_AUDIT_2026-11-08.md:27`).
- **Impact / Blast Radius**: Direct API calls can create and approve payouts with missing bank details, and concurrent profile edits can cause an admin to transfer funds to a different account than originally requested with no historical snapshot.
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
- **Minimal Fix**: Enforce non-blank `bankName` and `bankAccountNumber` on the locked `driver` in both `WithdrawalService#create` and `WithdrawalService#review(APPROVE)`, and add Flyway snapshot columns (`bank_name`, `bank_account_number`) on `withdrawal_requests` populated at `create`.
- **Proposed Regression Test**: Unit/Postgres test asserting `WithdrawalService#create` and `WithdrawalService#review(APPROVE)` reject drivers with blank `bankName`/`bankAccountNumber`, and that updating driver bank info after `create` does not alter the request's snapshotted payout destination.

### `F-008` — Legacy `GET /api/driver/wallet` Mixes `CREDIT` Transactions Into `CASH` Wallet Balance Response
- **Category**: API Contract / Ledger Consistency
- **Task ID**: `1.15` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/payment/service/PaymentService.kt:73-92` (`DriverWalletController#getWallet`)
- **Actor / Entrypoint**: `DRIVER` via `GET /api/driver/wallet`
- **Expected Behavior** *(source: `docs/WALLET_MODULE.md:30,132`)*: `CREDIT` and `CASH` driver wallets are independent; a response reporting `incomeBalance` (`CASH` wallet) must not mix `CREDIT` ledger entries and `CREDIT` `balance_after` values without distinguishing `walletType`.
- **Actual Behavior**: `PaymentService#getDriverWallet` returns `driver.incomeBalance` (`CASH` balance) paired with `SELECT id, ride_id, type, amount, balance_after, description, created_at FROM wallet_transactions WHERE driver_id = ? ORDER BY created_at DESC, id DESC LIMIT 100` — omitting both `AND wallet_type = 'CASH'` and the `wallet_type` column in `WalletTransactionResponse`. Running balances (`balance_after`) jump erratically between `CREDIT` and `CASH` totals.
- **Root Cause**: Legacy pre-V18 query was not filtered by `wallet_type = 'CASH'` after `CREDIT` and `CASH` wallets were separated.
- **Impact / Blast Radius**: Any legacy client calling `GET /api/driver/wallet` displays corrupted running balances (`balance_after`) and mixes commission debits into income history. (Newer clients use `GET /api/wallet/overview` and `GET /api/wallet/transactions?walletType=...`.)
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P3` Low**
- **Minimal Fix**: Filter `AND wallet_type = 'CASH'` in `PaymentService#getDriverWallet` (or deprecate/remove if unused by mobile clients — verify in Phase 3.01).
- **Proposed Regression Test**: Test seeding both `CREDIT` and `CASH` transactions for driver `7` and asserting `GET /api/driver/wallet` returns only `CASH` transactions matching `incomeBalance`.
