## 2. Conversation Lifecycle & State Machine (Source-Derived)

Conversations have no dedicated status column; lifecycle is derived from `(conversations(ride_id, driver_id), rides.status, rides.driver_id)`:

| Effective State | Condition | Allowed Actions |
|---|---|---|
| **`NONE`** | `rides.status ∈ {PENDING, SEARCHING}` (before first driver assignment) or `ride.driverId == null` | `GET messages` → empty page; `PUT read` → `0`; `POST messages` & `GET upload signature (CHAT)` → `409 CHAT_NOT_AVAILABLE`. |
| **`OPEN`** | `conversations(ride_id, ride.driver_id)` upserted in `RideStateMachine#tryAssignDriver:245` or `adminAssignDriver:303` AND `rides.status ∈ {DRIVER_ASSIGNED, DRIVER_ARRIVING, DRIVER_ARRIVED, VEHICLE_HANDOVER, IN_PROGRESS, ARRIVED_DESTINATION, VEHICLE_RETURNED}` | Customer & current assigned driver: `GET messages`, `POST messages` (`TEXT`/`IMAGE`), `PUT read`, `GET upload signature (CHAT)`. Admin: `GET /api/admin/rides/{id}/chat`. |
| **`PRESERVED_ARCHIVED`** *(reassigned)* | Driver A cancelled (`retryDispatch`) or Admin reassigned to Driver B (`V17` preserves `(ride_id, driver_A)` row) | Driver A immediately gets `404 RIDE_NOT_FOUND` on all chat/upload APIs (`ride.driverId != A`). Driver B gets a fresh `(ride_id, driver_B)` row (zero leakage). **Admin cannot query Driver A's preserved thread once Driver B is assigned (`F-036`)**. |
| **`CLOSED` (Read-Only)** | `rides.status ∈ {COMPLETED, CANCELLED, NO_DRIVER_FOUND, EXPIRED, FAILED_SYSTEM}` | `POST messages` & `GET upload signature (CHAT)` → `409 CHAT_CLOSED`. `GET messages` & `PUT read` remain allowed for customer & last assigned driver (to view history / clear unread badge). |

## 3. Authorization, Ownership & Message Validation

- **HTTP Authorization (`FirebaseSecurityConfig` + `@PreAuthorize` + `ConversationService#requireParticipant`)**:
  - `ChatController` enforces `@PreAuthorize("hasAnyRole('CUSTOMER','DRIVER')")`. `AdminRideController` enforces `hasRole('ADMIN')` (`F`+`C`) + `actor.role == Role.ADMIN` (`ChatService.kt:122`).
  - `ConversationService#requireParticipant` (`ConversationService.kt:40-57`) verifies `ride.customerId == actor.id` (for `CUSTOMER`) or `ride.driverId == actor.id` (for `DRIVER`), returning `404 RIDE_NOT_FOUND` for outsiders or reassigned prior drivers (no ride-existence oracle).
  - No arbitrary `conversationId` input exists; `senderId` and `senderRole` are derived strictly from `@CurrentUser actor` (`ChatService.kt:72-73`).
  - **Deleted/Banned accounts**: `CUSTOMER` with `status != ACTIVE` or `deletedAt != null` is rejected at `FirebaseAuthFilter` (`401/403`); `DRIVER` with `deletedAt != null` is rejected. `BLOCKED` drivers can still read past chat history (`OBS-11` — cannot send on closed rides).
- **Message Validation (`SendMessageRequest.kt:9-26`, `ChatService.kt:227-248`)**:
  - `clientMessageId`: required `UUID`. `content`: `@Size(max = 1000)`; `TEXT` requires non-blank trimmed text and rejects attachments. `IMAGE` requires non-blank `attachmentUrl` (≤2048) & `attachmentPublicId` (≤512), validated via `CloudinaryAssetService`.
  - Server timestamp: `now()` in PostgreSQL (`ChatMessageWriter.kt:27`); DB `CHECK` constraints enforce `ck_chat_messages_content` and `ck_chat_messages_sender` (`V1__init.sql:27-28`).
  - **SQLi / XSS**: All queries use parameterized JPA/JDBC bind params (zero dynamic SQL). Backend stores/returns raw UTF-8 JSON; Admin Web must escape `content` when rendering.

## 4. Concurrency, Ordering, Idempotency & Performance

| Race Scenario | Interleaving (`T1` / `T2`) & Outcome | Verdict |
|---|---|---|
| **Simultaneous send (Customer vs Driver) or duplicate retry** | `ChatService#send` acquires `rideRepository.findByIdForUpdate(rideId)` (`lockRide = true`, `ChatService.kt:60`) before inserting. `T1` locks `rides(id)`, inserts with `ON CONFLICT (conversation_id, client_message_id) WHERE client_message_id IS NOT NULL DO NOTHING RETURNING id`, commits. `T2` unblocks, hits idempotency check (`200 OK`, `duplicated = true`, no duplicate `ChatMessageCreated` event) or gets next monotonic `id`. | **SAFE** *(Minor note: `rateLimiter.check(actor)` runs while holding `rides FOR UPDATE` and before the idempotency lookup, so retries consume 1/20 quota.)* |
| **Send vs Ride Cancel / Complete / Admin Reassign** | `RideStateMachine#transition` and `adminAssignDriver` both lock `rides FOR UPDATE`. If `T1` (send) commits first, message is valid before close/reassign; `ChatPushListener` re-checks `ride.driverId == conversation.driverId` (`ChatService.kt:160`), suppressing stale push to old driver. If `T2` commits first, `T1` gets `409 CHAT_CLOSED` or `404 RIDE_NOT_FOUND`. | **SAFE** |
| **Send vs Account Deletion** | `AccountDeletionService` rejects deletion while non-terminal rides exist; only the `F-024` unlocked-read race window applies (already tracked in `F-024`). | **Tracked (`F-024`)** |
| **Read history / `markRead` vs Message Insertion** | Cursor pagination (`beforeId`/`afterId`, `size ∈ 1..100`, `size + 1` fetch) uses `idx_chat_conv_id (conversation_id, id DESC)` — O(1) seek, zero N+1, zero unbounded scan. `afterId` returns `id ASC` for clean reconnect gap-fill. `markRead` updates `WHERE read_at IS NULL AND sender_role <> :me AND id <= :upTo` using `idx_chat_unread`. | **SAFE** |
| **DB Commit Succeeds, Push Fails** | `ChatPushListener` runs `@Async("chatTaskExecutor")` in `AFTER_COMMIT` and wraps both `stompChannel` and `fcmChannel` in `runCatching`. DB commit is never rolled back; clients reconcile via `GET /api/chat/rides/{rideId}/messages?afterId=...`. | **SAFE** |
| **Multiple Devices Same Account** | `StompChannel` delivers to all active STOMP sessions for `CUSTOMER:{id}` / `DRIVER:{id}`; `FcmChannel` loops over all registered `device_tokens` for `(role, ownerId)`. Foreground deduplication uses shared `WsEnvelope.messageId` (`apns-collapse-id` & Android `tag`). | **SAFE** |

## 6. Confirmed Finding (`1.19`) & Open Product Decision

### F-036 (`P3` — `CONFIRMED` *(source)*) — Admin Dispute Blind Spot: Prior Driver's Preserved Conversation Unreachable After Reassignment
- **ID / Severity / Confidence**: `F-036` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [ChatService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/chat/service/ChatService.kt#L114-L129), [AdminRideController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/admin/controller/AdminRideController.kt#L51-L59), [ConversationRepository.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/chat/repository/ConversationRepository.kt#L6-L9)
- **Affected Flow**: `1.19` (In-Ride Chat) / `1.18` (Admin Dispute Review)
- **Preconditions**: Driver A is assigned to ride `R` and exchanges messages with Customer; Driver A then cancels (`retryDispatch`) or Admin reassigns `R` to Driver B (`V17__preserve_conversations_on_redispatch.sql` preserves Driver A's conversation row).
- **Expected Behavior**: Admin investigating a dispute/incident on ride `R` can list and inspect all preserved conversations `(ride_id, driver_id)` for ride `R`, not only the currently assigned driver's thread.
- **Actual Behavior**: `ChatService#adminMessages` resolves only `conversationService.forAssignment(ride)` when `ride.driverId != null` (or `findFirstByRideIdOrderByIdDesc(rideId)` when `driverId == null`), and `GET /api/admin/rides/{id}/chat` accepts no `driverId`/`conversationId` filter and has no list-conversations endpoint. Driver A's preserved messages become unreachable through every API.
- **Root Cause**: `ConversationRepository` only exposes `findByRideIdAndDriverId` and `findFirstByRideIdOrderByIdDesc`, and `AdminRideController#chatHistory` assumes a single active thread per ride despite `V17` introducing multi-conversation-per-ride preservation.
- **Reproduction Scenario**: Assign Driver A to ride `R` → Driver A sends abusive message → Admin reassigns ride `R` to Driver B → Admin calls `GET /api/admin/rides/{R}/chat` → receives empty `messages: []` (Driver B's new thread); Driver A's thread cannot be queried.
- **Impact**: Operational/dispute-resolution blind spot whenever an incident occurs before redispatch/reassignment (requires direct DB access to retrieve evidence).
- **Recommended Fix**: Add `GET /api/admin/rides/{id}/conversations` (returning `(conversationId, driverId, createdAt, messageCount)`) and an optional `driverId`/`conversationId` query parameter on `GET /api/admin/rides/{id}/chat`.
- **Suggested Regression Test**: PostgreSQL integration test assigning Driver A → sending message → reassigning to Driver B → asserting Admin can retrieve both Driver A's and Driver B's conversations while Driver B can only read Driver B's conversation.

### OBS-13 (`PRODUCT_DECISION_REQUIRED`) — Chat Retention, Media Deletion on Account Deletion & Admin Read Audit
- `AccountDeletionService` (`AccountDeletionService.kt:48-138`) does not delete/anonymize `conversations`/`chat_messages` or enqueue `chat_messages.cloudinary_public_id` for Cloudinary cleanup, and `GET /api/admin/rides/{id}/chat` writes no admin access audit log. Product/legal policy is required to define retention duration, anonymization vs dispute-evidence preservation, orphan chat upload cleanup, and admin read-audit requirements.
