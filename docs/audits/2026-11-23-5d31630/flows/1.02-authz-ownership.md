## 2. New Confirmed Findings (Task 1.02)

### `F-014` — Unrestricted STOMP `SEND` Destination Allows Any Authenticated User to Spoof Messages Into Another User's `/user/{victim}/queue/**`
- **Category**: Authorization Bypass / WebSocket STOMP Injection
- **Task ID**: `1.02` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/notification/ws/StompAuthInterceptor.kt:31-40` & `NotificationWebSocketConfig.kt:30-36`
- **Actor / Entrypoint**: Any authenticated `CUSTOMER` or `DRIVER` connected to `/ws-location` via STOMP `SEND`
- **Preconditions**: Victim (e.g., `customer:1` or `driver:7`) is connected to `/ws-location` and subscribed to `/user/queue/trip` or `/user/queue/rides/42/location`.
- **Expected Authorization**: Client `SEND` frames must ONLY be allowed to application destinations (`/app/**`, specifically `/app/location` for `DRIVER`s) and never directly to broker/user destinations (`/user/**`, `/queue/**`, `/topic/**`).
- **Actual Behavior**:
  - `StompAuthInterceptor.kt:33-38`:
    ```kotlin
    StompCommand.SUBSCRIBE -> {
        requireAuthenticated(accessor)
        requireAllowedDestination(accessor) // checks "/user/queue/"
    }
    StompCommand.SEND -> requireAuthenticated(accessor) // NO destination check!
    ```
  - `NotificationWebSocketConfig.kt:31-35` enables `SimpleBroker("/queue", "/topic")` and `UserDestinationPrefix("/user")`.
  - When an attacker sends a STOMP `SEND` frame with `destination: /user/driver:7/queue/trip` (or `/user/customer:1/queue/trip`, or `/user/customer:1/queue/rides/42/location`), `StompAuthInterceptor` allows it, and Spring's `UserDestinationMessageHandler` resolves `/user/driver:7/queue/trip` to victim `driver:7`'s active session queue and delivers the attacker's arbitrary JSON payload directly to the victim's mobile app!
- **Safe Reproduction (Fake Data)**:
  1. Connect as `customer:2` (`Authorization: Bearer <fake-token-c2>`), and connect victim `customer:1` subscribed to `/user/queue/trip`.
  2. From `customer:2`'s STOMP session, send `SEND` to `destination:/user/customer:1/queue/trip` with body `{"type":"PAYMENT_UPDATED","rideId":42,"method":"WALLET","status":"PAID"}`.
  3. Victim `customer:1` receives the forged frame on `/user/queue/trip` as if sent by the backend.
- **Root Cause**: Missing destination prefix allowlist on `StompCommand.SEND` in `StompAuthInterceptor#preSend`.
- **Impact / Blast Radius**: Any registered customer or driver can forge live ride offers, cancellation/completion notices, payment-paid confirmations (potentially tricking a driver into skipping cash collection), or fake live GPS updates to any victim whose numeric ID is enumerated (`customer:1..N`, `driver:1..N`).
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P1` High**
- **Minimal Fix**: In `StompAuthInterceptor#preSend`, for `StompCommand.SEND`, enforce `destination == "/app/location"` (or `destination.startsWith("/app/")`) and verify `(accessor.user as? StompPrincipal)?.recipient is Recipient.Driver`.
- **Proposed Regression Test**: Spring STOMP test asserting `StompAuthInterceptor#preSend` throws `MessagingException` when `SEND` targets `/user/customer:1/queue/trip`, `/queue/trip`, or `/topic/test`, and allows `SEND /app/location` only for `Recipient.Driver`.

### `F-015` — Default Production Profile (`production`) Leaves Swagger/OpenAPI Publicly Exposed and Actuator Health Details Unmasked (`OBS-03`)
- **Category**: Security Misconfiguration / Information Disclosure
- **Task ID**: `1.02` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `docker-compose.production.yml:6`, `src/main/resources/application-production.properties:1`, `src/main/resources/application-prod.properties:1-4`, `auth/security/FirebaseSecurityConfig.kt:52-53`
- **Actor / Entrypoint**: Anonymous user via `GET /v3/api-docs`, `GET /swagger-ui/index.html`, `GET /actuator/health`
- **Expected Authorization**: In production deployment, OpenAPI/Swagger endpoints should be disabled and Actuator health details hidden (`show-details=never`).
- **Actual Behavior**: `docker-compose.production.yml:6` sets `SPRING_PROFILES_ACTIVE: ${SPRING_PROFILES_ACTIVE:-production}`, which loads `application-production.properties` (only sets `app.verification.require-protected-storage=true`). Meanwhile, `springdoc.api-docs.enabled=false`, `springdoc.swagger-ui.enabled=false`, and `management.endpoint.health.show-details=never` are placed in `application-prod.properties` (profile `prod`), and `FirebaseSecurityConfig.kt:53` sets `.permitAll()` on `/v3/api-docs/**` and `/swagger-ui/**`.
- **Root Cause**: Profile name mismatch between `docker-compose.production.yml` (`production`) and `application-prod.properties` (`prod`).
- **Impact**: Default production containers expose full internal/admin API schema and Swagger UI to anonymous callers.
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
- **Minimal Fix**: Consolidate `application-prod.properties` settings into `application-production.properties` (or set `SPRING_PROFILES_ACTIVE=production,prod` in `docker-compose.production.yml`), and restrict `/v3/api-docs/**` & `/swagger-ui/**` to non-production profiles.
- **Proposed Regression Test**: Spring Boot test with `@ActiveProfiles("production")` asserting `/v3/api-docs` and `/swagger-ui/index.html` return `404`/`403` and `/actuator/health` omits component details.

### `F-016` — Revoked Firebase ID Tokens Accepted on HTTP & STOMP, and Existing STOMP Sessions Persist After Account Ban/Deletion (`OBS-04`)
- **Category**: Authentication / Session Revocation
- **Task ID**: `1.02` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `auth/security/FirebaseAuthFilter.kt:31`, `notification/ws/FirebaseAuthTokenVerifier.kt:15`, `notification/ws/StompAuthInterceptor.kt:33-40`
- **Actor / Entrypoint**: User with revoked Firebase token on any HTTP endpoint or STOMP `CONNECT`; or banned/deleted user with an already-open STOMP session
- **Expected Authorization** *(source: `AuthService.kt` `verifyToken(idToken)` passes `checkRevoked = true`; `AdminCustomerService.kt:183` explicitly calls `firebaseAuth.revokeRefreshTokens(firebaseUid)` on ban)*: Revoked tokens must be rejected on protected APIs, and banned/deleted accounts must not retain active STOMP sessions.
- **Actual Behavior**:
  1. `FirebaseAuthFilter.kt:31` calls `firebaseAuth.verifyIdToken(idToken)` (default `checkRevoked = false`) and `FirebaseAuthTokenVerifier.kt:15` calls `firebaseAuth.verifyIdToken(token)` (default `checkRevoked = false`). An active user whose Firebase tokens were revoked (e.g., compromised device, password reset, admin revoke) remains authenticated for up to 1 hour until token expiry.
  2. `StompAuthInterceptor.kt:33-40` only authenticates on `CONNECT`; once connected, a banned customer or deleted driver keeps their open STOMP session indefinitely and continues receiving `/user/queue/**` updates and sending `/app/location` frames.
- **Root Cause**: Omission of `checkRevoked = true` in HTTP/STOMP token verification filters and absence of STOMP session disconnect/revalidation on account ban/delete.
- **Impact**: Delayed session invalidation (up to 1h on HTTP for revoked tokens; indefinite on open STOMP sockets after ban/delete).
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
- **Minimal Fix**: Pass `checkRevoked = true` (or cache revocation timestamp / check DB `status` with short TTL) in `FirebaseAuthFilter` and `FirebaseAuthTokenVerifier`, and close active STOMP sessions (or re-verify `authenticatedUserProvider` periodically / on `SEND`) when an account is banned or deleted.
- **Proposed Regression Test**: Unit test mocking `FirebaseAuth.verifyIdToken(token, true)` throwing `FirebaseAuthException(REVOKED_ID_TOKEN)` and asserting `FirebaseAuthFilter` clears `SecurityContextHolder` (`401`).
