## 1. Inventory & Legacy-vs-Threaded Architecture

Legacy and threaded APIs are **NOT independent systems** — both share the same PostgreSQL tables (`support_tickets`, `support_ticket_images`, `support_ticket_messages`), and **both sets of endpoints remain live**:

| Layer | Legacy API (`support/*`) | Threaded API (`support/ticket/*`) | Shared Persistence / Coupling |
|---|---|---|---|
| **Member Routes** | `POST/GET /api/support/tickets`, `GET /api/support/tickets/{id}` | `POST/GET /api/tickets`, `GET /api/tickets/{id}`, `GET/POST /api/tickets/{id}/messages` | `TicketService#create/list/detail/messages` delegate directly to `SupportService#create/list/detail`. `SupportService#create` seeds the first row in `support_ticket_messages`. |
| **Admin Routes** | `GET /api/admin/support/tickets`, `GET/PATCH /api/admin/support/tickets/{id}` | `GET /api/admin/tickets`, `GET /api/admin/tickets/{id}`, `POST /api/admin/tickets/{id}/claim`, `POST /api/admin/tickets/{id}/messages` | Both mutate `support_tickets` and insert into `support_ticket_messages` — **but with divergent guards & notification behavior (`F-038`)**. |
| **Schema (`V14`, `V25`, `V26`)** | `support_tickets` (`UNIQUE(owner_id, owner_role, client_request_id)`, `CHECK status IN ('OPEN','IN_PROGRESS','WAITING_FOR_USER','RESOLVED','CLOSED')`, `ride_id FK rides(id)`), `support_ticket_images` | `support_ticket_messages` (`ticket_id FK ON DELETE CASCADE`, `CHECK (length(btrim(body)) > 0 OR image_url IS NOT NULL)`, `idx_support_ticket_messages_ticket (ticket_id, id)`) | No `client_message_id` on `support_ticket_messages`; no FK on `handled_by` or `(owner_id, owner_role)` (polymorphic). |
| **Notifications** | None (`SupportService#update` publishes **no** event — `F-038`) | `TicketService#sendAdminMessage` publishes `TicketReplied` → `TicketNotificationListener` (`AFTER_COMMIT`) → `TicketNotificationSender` (`REQUIRES_NEW`) → `NotificationPort` (STOMP + FCM + `notifications` table) | `TicketReplyPayload`: title `"Hỗ trợ khách hàng: Có phản hồi mới"`, body truncated to 50 chars (`"Đã gửi một hình ảnh"` if blank). |

## 2. Ticket State Machine (Source-Derived)

| Actor | Current State | Action / Endpoint | Guard | Next State | Side Effects |
|---|---|---|---|---|---|
| `CUSTOMER` / `DRIVER` | *(none)* | `POST /api/support/tickets` or `/api/tickets` | Valid category (`TRIP`/`PAYMENT`/`HANDOVER`/`ACCOUNT`/`OTHER`), desc `10..4000`, `rideId` owned if set, ≤5 Cloudinary-validated images (legacy) | `OPEN` | Inserts `support_tickets` (`ON CONFLICT DO NOTHING` by `client_request_id`), `support_ticket_images`, seed `support_ticket_messages` |
| `ADMIN` | `OPEN` / `WAITING_FOR_USER` / `IN_PROGRESS(handled_by=null)` | `POST /api/admin/tickets/{id}/claim` | `findForUpdate(id)`; rejects `409` if `IN_PROGRESS && handled_by != null && handled_by != admin.id` | `IN_PROGRESS` (`handled_by=admin.id`) | No-op on `RESOLVED`/`CLOSED` (returns detail unchanged) |
| `ADMIN` | Any *(except `IN_PROGRESS` claimed by another admin)* | `POST /api/admin/tickets/{id}/messages` | `findForUpdate(id)`; claim guard; `status ∈ ADMIN_STATUSES` (default `WAITING_FOR_USER`); `validateMessage` (**`F-028`**) | Requested `TicketStatus` | Inserts `support_ticket_messages`, updates `status`/`handled_by`/`response`, publishes `TicketReplied` (`AFTER_COMMIT`) |
| `ADMIN` | **Any (no claim guard!)** | `PATCH /api/admin/support/tickets/{id}` *(legacy)* | `FOR UPDATE`; optional `expectedUpdatedAt`; `RESOLVED` requires non-blank `response` (`CLOSED` does not) | Requested status | Updates `status`/`response`/`handled_by=actor.id`, inserts message if non-blank; **drops `TicketReplied` notification (`F-038`)** |
| `CUSTOMER` / `DRIVER` | **Any (including `CLOSED`!)** | `POST /api/tickets/{id}/messages` | `support.detail(actor, id)` (owner check only — **no `FOR UPDATE`, no `CLOSED` guard — `F-037`**); `validateMessage` (**`F-028`**) | **`OPEN` (`handled_by=NULL`)** | Inserts `support_ticket_messages`; unconditionally resets `status='OPEN', handled_by=NULL` |

## 3. Confirmed Findings (`1.20`)

### F-037 (`P2` — `CONFIRMED` *(source)*) — `TicketService#sendUserMessage` Lacks Row Lock (`FOR UPDATE`) and `CLOSED` Status Guard, Allowing Unconditional Reopen of Closed Tickets & Lost-Update Races
- **ID / Severity / Confidence**: `F-037` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [TicketService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/ticket/TicketService.kt#L61-L75)
- **Affected Flow**: `1.20` (Threaded Support Tickets — User Reply & Lifecycle)
- **Preconditions**: Any `CUSTOMER` or `DRIVER` owns a ticket `T` that is `CLOSED` (or concurrently being claimed/closed by an `ADMIN`).
- **Expected Behavior**: (1) Replying to a `CLOSED` ticket is rejected with `409 Conflict` (or explicit reopen rule), and (2) `sendUserMessage` locks `support_tickets` via `tickets.findForUpdate(id)` before checking status and inserting the message so it cannot race against `claim` / `sendAdminMessage`.
- **Actual Behavior**: `sendUserMessage` only calls `support.detail(actor, id)` (read-only, unlocked) without checking `ticket.status`, inserts `TicketMessageEntity`, and unconditionally executes `UPDATE support_tickets SET status = 'OPEN', handled_by = NULL WHERE id = ?`.
- **Root Cause**: Missing `tickets.findForUpdate(id)` lock and missing `if (ticket.status == TicketStatus.CLOSED) throw ConflictException(...)` check in `TicketService#sendUserMessage`.
- **Reproduction Scenario (T1/T2 Race & Closed Reopen)**:
  1. *Closed Reopen*: Admin closes ticket `T` (`status = CLOSED`). Customer calls `POST /api/tickets/{T}/messages` → succeeds (`200 OK`) and resets `T` to `OPEN, handled_by = NULL`.
  2. *T1/T2 Interleaving*: `T1` (`sendUserMessage`) passes `support.detail` and inserts message; `T2` (`sendAdminMessage(CLOSED)` or `claim`) locks `T FOR UPDATE`, sets `CLOSED`/`IN_PROGRESS` + `handled_by = adminId`, commits and sends `TicketReplied(CLOSED)`; `T1`'s `UPDATE` then acquires the row lock and overwrites `status = OPEN, handled_by = NULL` — silently undoing the admin's close/claim.
- **Impact**: Broken ticket terminal state (`CLOSED` tickets can be infinitely reopened by spamming replies) and lost-update races that wipe admin `claim`/`CLOSED` decisions.
- **Recommended Fix**: Lock ticket with `tickets.findForUpdate(id)`, verify ownership (`ownerId == actor.id && ownerRole == actor.role`), reject `TicketStatus.CLOSED` with `409`, then insert message and update status.
- **Suggested Regression Test**: Unit + PostgreSQL concurrency test verifying `POST /api/tickets/{id}/messages` returns `409` on `CLOSED` tickets and serializes cleanly with `claim` / `sendAdminMessage`.

### F-038 (`P2` — `CONFIRMED` *(source)*) — Legacy `PATCH /api/admin/support/tickets/{id}` Bypasses Admin Claim Ownership, Silently Drops `TicketReplied` Notifications, and Allows `CLOSED` Without Response
- **ID / Severity / Confidence**: `F-038` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [SupportService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/SupportService.kt#L86-L106), [SupportController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/SupportController.kt#L21-L23)
- **Affected Flow**: `1.20` (Legacy vs Threaded Admin Ticket Processing)
- **Preconditions**: Ticket `T` is claimed (`IN_PROGRESS, handled_by = adminA`) or any admin uses legacy `PATCH /api/admin/support/tickets/{id}`.
- **Expected Behavior**: Legacy `SupportService#update` enforces the same claim-ownership guard (`409` when `IN_PROGRESS` and `handled_by != actor.id`), validates closing responses consistently for both `RESOLVED` and `CLOSED`, and publishes `TicketReplied` so the ticket owner is notified.
- **Actual Behavior**:
  1. Never checks `status == IN_PROGRESS && handled_by != null && handled_by != actor.id`; because `expectedUpdatedAt` defaults to `null`, Admin B can overwrite Admin A's actively claimed ticket and steal `handled_by`.
  2. Writes to `support_ticket_messages` and updates `support_tickets` **without publishing `TicketReplied`**, causing silent notification loss (0 STOMP/FCM/in-app alerts).
  3. Enforces non-blank `response` only for `RESOLVED` (`L89`), permitting `CLOSED` with `response = null`/blank.
- **Root Cause**: Threaded workflow (`TicketService`) added claim locking and `TicketReplied` events without retrofitting or deprecating `SupportService#update`.
- **Reproduction Scenario**: Admin A claims ticket `T` (`POST /api/admin/tickets/{T}/claim` → `IN_PROGRESS, handled_by=A`). Admin B calls `PATCH /api/admin/support/tickets/{T}` with `{"status":"CLOSED","response":""}` → returns `200 OK`, overwrites `handled_by=B`, closes `T` without response, and sends 0 notifications to the customer.
- **Impact**: Concurrent admin collisions on claimed disputes, silent customer/driver notification loss, and bypassed response validation.
- **Recommended Fix**: Add claim-ownership check in `SupportService#update` (or delegate to `TicketService`), publish `TicketReplied` after commit when status/response changes, and enforce response requirement on `CLOSED` (or deprecate/remove the legacy PATCH route).
- **Suggested Regression Test**: PostgreSQL test asserting Admin B gets `409` on `PATCH /api/admin/support/tickets/{id}` when Admin A holds `IN_PROGRESS`, and verifying `TicketReplied` is published on legacy updates.

### F-039 (`P3` — `CONFIRMED` *(source)*) — N+1 Image Query in `SupportService#list`, Unbounded Ticket Message History, and Missing Message Idempotency Key
- **ID / Severity / Confidence**: `F-039` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [SupportService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/SupportService.kt#L74-L75, L109-L115), [TicketService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/ticket/TicketService.kt#L66, L109, L183-L184), [TicketDtos.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/ticket/TicketDtos.kt#L53-L63)
- **Affected Flow**: `1.20` (Support Ticket Listing, History & Reply Reliability)
- **Preconditions**: A user/admin lists 20 tickets, opens a long ticket thread, or retries a `POST /messages` call after a network timeout.
- **Expected Behavior**: Batch-loaded images (2 queries/page), paginated message history (`beforeId`/`afterId`/`size`), and idempotent `clientMessageId` deduplication (matching in-ride chat `V9`).
- **Actual Behavior**:
  1. `SupportService#list` runs 1 query + 20 per-row `SELECT ... FROM support_ticket_images WHERE ticket_id=?` queries (21 queries/page; also impacts `TicketService#list`).
  2. `TicketService#messageDtos` (`findByTicketIdOrderByCreatedAtAscIdAsc`) loads **all** messages without `LIMIT` on every detail/messages fetch.
  3. `support_ticket_messages` has no `client_message_id` unique key — network retries insert duplicate messages and trigger duplicate `TicketReplied` FCM/STOMP pushes.
- **Root Cause**: Legacy `map(r)` nested JDBC query, unpaginated JPA query, and omitted `client_message_id` in `V25`.
- **Reproduction Scenario**: Retry `POST /api/admin/tickets/{id}/messages` twice after a timeout → 2 identical admin messages persisted and 2 identical FCM notifications delivered.
- **Impact**: DB connection amplification (HikariCP pool=10), memory/latency growth on long threads, and duplicate replies/notifications on flaky mobile networks.
- **Recommended Fix**: Batch-fetch images with `WHERE ticket_id = ANY(?)`, add cursor pagination to `/messages`, and add optional `client_message_id` partial unique index on `support_ticket_messages`.
- **Suggested Regression Test**: Test verifying `POST /api/tickets/{id}/messages` with identical `clientMessageId` inserts 1 row and `GET /messages` respects `size` pagination.
