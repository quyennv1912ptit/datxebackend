## 3. Audit of `OBS-08` (`readOnly = true` Calling `REQUIRES_NEW` `grantWelcome`)

- **Proxy / self-invocation**: `VoucherService#listAvailable` (`@Transactional(readOnly = true)`, `VoucherService.kt:52`) invokes `grantService.grantWelcome(actor.id)` on a **separate Spring bean** (`VoucherGrantService`, `@Transactional(propagation = Propagation.REQUIRES_NEW)`, `VoucherGrantService.kt:14`). Spring AOP proxy **does** intercept the call (not self-invocation).
- **Duplicate grant concurrency**: Safe — `VoucherGrantService.kt:45-54` locks `customers(id) FOR UPDATE` before checking `alreadyGranted`.
- **Actual bug (`F-013`)**: On **every** `GET /api/customer/vouchers` call (even for returning customers who already have the welcome voucher), `listAvailable` holds read-only connection `C1` open while `REQUIRES_NEW` attempts to borrow a **second** connection `C2` from HikariCP. When concurrent calls reach `hikari.maximumPoolSize` (default 10), all threads hold `C1` and block waiting for `C2`, causing **connection-pool self-deadlock** until `connectionTimeout` (30s)!

## 5. New Confirmed Findings (Task 1.14)

### `F-009` — `PromoBudgetService#setLimit` Lacks `FOR UPDATE` Lock (and `promo_budget` Lacks Cap CHECK), Allowing Negative `availableAmount`
- **Category**: Concurrency / Financial Invariant | **Task ID**: `1.14` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/voucher/service/PromoBudgetService.kt:21-38`; `V29__promo_budget_ledger.sql:4-11`
- **Actor / Entrypoint**: `ADMIN` via `PUT /api/admin/vouchers/budget` racing `reserveIssuance` / `hold`
- **Expected Behavior**: `budget_limit` must never drop below `held_amount + spent_amount + issuance_reserved` (`availableAmount >= 0`).
- **Actual Behavior**: `setLimit` calls `summary()` which selects `promo_budget WHERE id = 1` **without `FOR UPDATE`**, and `promo_budget` has no DB `CHECK(held_amount + spent_amount + issuance_reserved <= budget_limit)`.
  - **Interleaving**: Initial `limit=1,000,000, reserved=400,000`. `T1` (`setLimit(500,000)`) reads `reserved=400,000 <= 500,000`. `T2` (`reserveIssuance(300,000)`) locks `promo_budget(1)`, sets `reserved=700,000`, commits. `T1` updates `budget_limit=500,000`, commits → **`availableAmount = -200,000`**.
- **Root Cause**: Missing `FOR UPDATE` in `setLimit` and missing table-level CHECK constraint on `promo_budget`.
- **Impact**: Global promo budget cap can be breached under concurrent admin budget adjustment and voucher issuance/booking.
- **Confidence**: High | **Verdict**: `CONFIRMED` *(source)* | **Severity**: **`P2` Medium**
- **Minimal Fix**: Lock `promo_budget WHERE id = 1 FOR UPDATE` inside `setLimit` (instead of calling unlocked `summary()`) and add `CHECK (held_amount + spent_amount + issuance_reserved <= budget_limit)` after fixing `F-010`.
- **Proposed Regression Test**: Barrier concurrency test running `setLimit(500_000)` vs `reserveIssuance(300_000)` asserting `budget_limit >= held + spent + issuance_reserved`.

### `F-010` — `PromoBudgetService#release` Restores `holdAmount` Instead of `forecast_amount` to `issuance_reserved`, Enabling Promo Budget Exhaustion (DoS) via Book-Cancel Loop
- **Category**: Financial Accounting / Promo Budget DoS | **Task ID**: `1.14` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/voucher/service/PromoBudgetService.kt:285-298, 301-338`
- **Actor / Entrypoint**: `CUSTOMER` booking & cancelling a ride with any non-campaign voucher (e.g., Welcome / Milestone / Admin personal voucher) where `discountAmount > forecast_reserve_per_use` (`maxDiscount / 2`)
- **Expected Behavior**: Booking and immediately cancelling a ride must leave `promo_budget.issuance_reserved` and `availableAmount` **unchanged** (net zero).
- **Actual Behavior**:
  - At booking (`PromoBudgetService.kt:286`), `hold()` subtracts **`forecast`** (`maxDiscount / 2`, e.g., `15,000`) from `issuance_reserved` and adds **`amount`** (`30,000`) to `held_amount`.
  - At cancel (`PromoBudgetService.kt:332-338`), `release()` subtracts `holdAmount` (`30,000`) from `held_amount`, **but adds `holdAmount` (`30,000`) instead of `forecast_amount` (`hold[1] = 15,000`) back to `issuance_reserved`**!
  - Every single book→cancel cycle permanently inflates `issuance_reserved` by `amount - forecast` (`+15,000 VND`) and shrinks `availableAmount` by `-15,000 VND` (and non-campaign vouchers have no expiry release job).
- **Reproduction (Fake Data)**:
  1. Set `promo_budget.budget_limit = 100,000`. Customer `1` gets Welcome Voucher (`20%`, `maxDiscount = 30,000`, `forecast = 15,000`) → `issuance_reserved = 15,000`, `available = 85,000`.
  2. Book Ride (`fare = 150,000`, `discount = 30,000`) → `issuance_reserved = 0`, `held = 30,000`.
  3. Cancel Ride → `held = 0`, **`issuance_reserved = 30,000`**, `available = 70,000` (`15,000` leaked!).
  4. Repeat 6 times → `issuance_reserved = 105,000 > budget_limit (100,000)` → `available = -5,000` → **entire platform promo budget permanently frozen!**
- **Root Cause**: Line 333 sets `canRestoreAmount = if (canRestore) holdAmount else 0L` for both campaign and non-campaign vouchers, ignoring `hold[1]` (`forecast_amount`) that was already queried on line 303!
- **Impact**: Any single customer with a Welcome Voucher can exhaust and permanently freeze the entire platform's `promo_budget` simply by booking and cancelling rides while `SEARCHING` (zero cost to the customer).
- **Confidence**: High | **Verdict**: `CONFIRMED` *(source)* | **Severity**: **`P1` High**
- **Minimal Fix**: In `PromoBudgetService#release`, restore `if (campaignId != null) holdAmount else (hold[1] as Long)` to `issuance_reserved` when `canRestore` is true.
- **Proposed Regression Test**: Postgres test running book → cancel 3 times with Welcome Voucher (`forecast=15,000, discount=30,000`), asserting `issuance_reserved == 15,000` and `availableAmount` is unchanged after every cycle.

### `F-011` — Claiming a Public Campaign Before Listing Vouchers Permanently Denies the Customer's Welcome Voucher
- **Category**: Business Logic / Voucher Grant Collision | **Task ID**: `1.14` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/voucher/service/VoucherGrantService.kt:56-71` & `VoucherService.kt:134`
- **Actor / Entrypoint**: `CUSTOMER` via `POST /api/customer/vouchers/campaigns/{id}/claim` followed by `GET /api/customer/vouchers`
- **Expected Behavior**: New customers receive their one-time Welcome Voucher regardless of whether they claimed a public campaign first.
- **Actual Behavior**: `VoucherService#claimCampaign` (`VoucherService.kt:134`) inserts claimed campaign vouchers with `source = 'SYSTEM_REWARD'` and **`milestone = 0`** (and `AdminVoucherService#create:302` does the same for admin-gifted personal vouchers). `VoucherGrantService#grant(customerId, milestone=0, WELCOME)` (`VoucherGrantService.kt:58-64`) checks `WHERE owner_customer_id = ? AND source = 'SYSTEM_REWARD' AND milestone = 0` without `AND campaign_id IS NULL` — returning `alreadyGranted = true` and permanently skipping the Welcome Voucher.
- **Root Cause**: Overloading `(source = 'SYSTEM_REWARD', milestone = 0)` for Welcome, claimed campaign, and admin personal vouchers without filtering `campaign_id IS NULL` (or a dedicated welcome marker).
- **Impact**: Every new customer who claims a campaign banner before opening their personal voucher list permanently loses their Welcome Voucher.
- **Confidence**: High | **Verdict**: `CONFIRMED` *(source)* | **Severity**: **`P2` Medium**
- **Minimal Fix**: Distinguish welcome grants explicitly (e.g., `AND campaign_id IS NULL` plus a dedicated `milestone` or `grant_type` column / check so admin personal vouchers also don't block welcome).
- **Proposed Regression Test**: Postgres test where new customer claims a campaign first, then calls `listAvailable`, asserting the Welcome Voucher is still granted.

### `F-013` — `VoucherService#listAvailable` Holds Outer Read-Only Connection While Invoking `REQUIRES_NEW` on Every Request (HikariCP Pool Deadlock Under Load)
- **Category**: Transaction Management / Reliability (`OBS-08`) | **Task ID**: `1.14` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/voucher/service/VoucherService.kt:52-57, 144-157` & `VoucherGrantService.kt:14-17`
- **Actor / Entrypoint**: `CUSTOMER` via `GET /api/customer/vouchers`
- **Expected Behavior**: A read-only listing endpoint must not hold 2 simultaneous DB connections per request and risk HikariCP pool starvation.
- **Actual Behavior**: `listAvailable` is annotated `@Transactional(readOnly = true)` (acquiring connection `C1`), then unconditionally calls `grantService.grantWelcome(actor.id)` (`@Transactional(REQUIRES_NEW)`, which suspends `C1` and acquires a second connection `C2` on **every** request, even for returning customers). When concurrent `GET /api/customer/vouchers` requests reach `hikari.maximumPoolSize` (default 10), all 10 hold `C1` and wait for `C2`, deadlocking the entire DB connection pool until `connectionTimeout` (30s).
- **Root Cause**: Unconditional nested `REQUIRES_NEW` call inside an outer `@Transactional(readOnly = true)` method.
- **Impact**: High-concurrency traffic to `GET /api/customer/vouchers` can exhaust the HikariCP pool and stall all backend database requests for 30s.
- **Confidence**: High | **Verdict**: `CONFIRMED` *(source)* | **Severity**: **`P2` Medium**
- **Minimal Fix**: Remove `@Transactional(readOnly = true)` from `VoucherService#listAvailable` (individual `JdbcTemplate` queries don't require an outer transaction across `grantWelcome`), or invoke `ensureWelcomeVoucher` before entering the read transaction.
- **Proposed Regression Test**: Concurrency test with small HikariCP pool (`maximumPoolSize = 2`) firing 4 concurrent `listAvailable` calls, asserting zero connection-timeout exceptions.
