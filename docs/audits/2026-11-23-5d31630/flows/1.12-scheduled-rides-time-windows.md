## 2. Timezone & Rollover Verification

- **Wire / Storage**: `CreateRideRequest.scheduledAt` is UTC `Instant` (offset-aware ISO-8601), stored in PostgreSQL `timestamptz` with `hibernate.jdbc.time_zone=UTC` (`application.properties:21`).
- **Window Comparisons**: All scheduler/dispatch/expiration comparisons use `Clock.instant()` (UTC `Instant`), completely immune to server local timezone, DST, or day/month/year rollovers.
- **Business-Zone Rules**:
  - `PricingRideQuoteService#isNight` (`L93-98`): evaluates `pricingAt = scheduledAt` in `ZoneId.of("Asia/Ho_Chi_Minh")` with overnight wrap-around (`start > end`).
  - `DriverVerificationEligibility#mayDriveForRide` (`L69`): evaluates driver CCCD/GPLX expiry on `maxOf(now, ride.scheduledAt ?: now)` in `Asia/Ho_Chi_Minh`, preventing a driver whose license expires before pickup day from accepting.

## 3. Concurrency, Edge Cases & Failure Recovery

| Scenario | Behavior & Serialization | Verdict |
|---|---|---|
| Two concurrent `SCHEDULED` bookings | Serialized by `customers FOR UPDATE` (`RideService.kt:63`) + `existsByCustomerIdAndTypeAndStatus(SCHEDULED, PENDING)` (`L81-85`). Second fails `409 SCHEDULED_RIDE_EXISTS`. Verified by `ScheduledRideBookingPostgresTests`. | **SAFE** |
| Scheduled ride (`PENDING`) + Instant ride | Allowed: `ACTIVE_RIDE_STATUSES` excludes `PENDING`. When scheduled window opens while instant ride is active, `ScheduledRideScheduler` defers activation until instant ride finishes (or expires at `T + 10m`). | **SAFE** |
| Multi-instance / overlapping `ScheduledRideScheduler` | Both instances lock `customers FOR UPDATE` → `rides FOR UPDATE` and re-check `ride.status == PENDING` (`L44-46`). Zero duplicate `START_SEARCH` or `EXPIRE`. | **SAFE** |
| Scheduler vs Cancel / Instant Booking | Lock order compatible (`customers → rides` vs `rides` on cancel, `customers` on booking) — zero deadlock; strictly serialized. | **SAFE** |
| Scheduler vs Account Deletion / `INACTIVE` | Active `PENDING` scheduled ride blocks `deleteCustomer` normally (race before lock tracked in `F-024`). However, `ScheduledRideScheduler` does **not** verify `customer.status == ACTIVE` after locking `customers` (**`F-030`**). | **Bug (`F-030`)** |
| Backend / Redis restart, missed tick, worker crash | All schedule state is durable in PostgreSQL (`rides.scheduled_at`, `ride_dispatch_outbox` with 60s lease + `FOR UPDATE SKIP LOCKED`, `RideDispatchRecoveryTask` every 10s). Missed ticks catch up on next poll (`scheduledAt <= now + 15m`) or expire cleanly if past `T + 10m`. | **SAFE** |
| Voucher, Pricing & Wallet on Scheduled Rides | Fare is locked at booking (`pricingAt = scheduledAt`); wallet is checked at booking (not held) and settled at completion (`OBS-01` fallback to `CASH` if balance drops). Voucher is consumed at booking (`now()`), NOT validated against `scheduledAt`, and `scheduledAt` has **no max horizon** (**`F-030`**). | **Bug (`F-030`)** |

## 4. Confirmed Findings (`1.12`)

### F-030 (`P2` — `CONFIRMED` *(source)*) — Unbounded `scheduledAt` Horizon Locks Promo/Campaign Budget Indefinitely
- **Location**: [RideCreationValidator.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideCreationValidator.kt#L64-L70); [VoucherService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/voucher/service/VoucherService.kt)
- **Root Cause**: `RideCreationValidator#validateSchedule` only checks `scheduledAt.isAfter(Instant.now())` (no maximum advance booking window), and `VoucherService#calculate` checks `voucher.validTo` against `now()` rather than `scheduledAt`.
- **Impact**: A customer can book a `SCHEDULED` ride arbitrarily far in the future (e.g., year 2099) using a voucher expiring today, locking `promo_budget.held_amount` and `voucher_campaign_budget.held_amount` indefinitely past campaign expiration.
- **Recommended Fix**: Enforce a configurable `app.scheduled-ride.max-advance-time` (e.g., 7 or 30 days) in `RideCreationValidator` and validate `voucher.validTo` against `scheduledAt`.

### F-031 (`P2` — `CONFIRMED` *(source)*) — `ScheduledRideScheduler` Dispatches Scheduled Rides for `INACTIVE` Customers
- **Location**: [ScheduledRideScheduler.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/ScheduledRideScheduler.kt#L44-L73); [AdminCustomerService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/admin/service/AdminCustomerService.kt#L163-L179)
- **Root Cause**: `ScheduledRideScheduler#processDueRides` (`L44`) locks `customers.findByIdForUpdate(candidate.customerId)` but only checks `.isEmpty` (omitting `customer.status == UserStatus.ACTIVE && customer.deletedAt == null`), while `AdminCustomerService#updateStatus` only cancels `PENDING` rides when `status == BANNED` (not `INACTIVE`).
- **Impact**: A customer moved to `INACTIVE` still has their `PENDING` scheduled ride automatically transitioned to `SEARCHING` and dispatched to drivers when the lead window opens.
- **Recommended Fix**: In `ScheduledRideScheduler`, check `customer.status == UserStatus.ACTIVE && customer.deletedAt == null` after locking `customers`, and expire/cancel the ride otherwise.
