## 2. Deep Verification of WebSocket / STOMP Security (`F-014` & `F-016`)

### 2.1 Framework Routing Proof for `F-014` (P1)
In [NotificationWebSocketConfig.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/notification/ws/NotificationWebSocketConfig.kt#L30-L36) & [StompAuthInterceptor.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/notification/ws/StompAuthInterceptor.kt#L31-L41):
1. `StompCommand.SUBSCRIBE` is restricted to `destination.startsWith("/user/queue/")` (`L33-36, L66-71`).
2. `StompCommand.SEND` calls **only** `requireAuthenticated(accessor)` (`L38`) with **no destination prefix restriction** (does not enforce `destination.startsWith("/app/")`).
3. In Spring's `AbstractMessageBrokerConfiguration`, `clientInboundChannel` fans out to three subscribers: `SimpAnnotationMethodMessageHandler` (`/app/**`), **`UserDestinationMessageHandler`** (`/user/**`), and **`SimpleBrokerMessageHandler`** (`/queue/**`, `/topic/**`).
4. When any authenticated user (`customer:10` or `driver:20`) sends STOMP `SEND` to `/user/driver:42/queue/trip` (or `/user/customer:99/queue/trip` or `/user/customer:99/queue/rides/5/location`), `UserDestinationMessageHandler` resolves `/user/driver:42/queue/trip` via `DefaultUserDestinationResolver` against `SimpUserRegistry` to `/queue/trip-user{victimSessionId}` and routes it onto `brokerChannel`, where `SimpleBrokerMessageHandler` delivers the forged frame directly into victim `driver:42`'s session — completely bypassing all `@MessageMapping` controllers.
5. **Recommended Isolated Negative Test**: Instantiate `StompAuthInterceptor` with a mock `AuthTokenVerifier` returning `Recipient.Customer(10)`, dispatch a `StompCommand.SEND` message targeting `/user/driver:42/queue/trip` and `/queue/trip`, and assert `MessagingException` is thrown (currently passes through!).

### 2.2 Token & Session Security (`F-016`)
- `FirebaseAuthTokenVerifier#verify` calls `firebaseAuth.verifyIdToken(token)` without `checkRevoked = true`, and `StompAuthInterceptor` only authenticates on `CONNECT` — active STOMP sessions persist indefinitely after admin ban or account deletion (`F-016`).
- `AuthenticatedUserCache` (3s JVM TTL) is bypassed only on roleless lookups; `StompAuthInterceptor` passes `roleHint` (`CUSTOMER`/`DRIVER`).

## 3. Confirmed Finding (`1.17`)

### F-033 (`P2` — `CONFIRMED` *(source)*) — `VoucherCampaignPublishedListener` Queries Non-Existent `users` Table Uncaught in `AFTER_COMMIT`, Breaking All Campaign Push Notifications & Failing Admin Publish HTTP Responses
- **ID / Severity / Confidence**: `F-033` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [VoucherCampaignPublishedListener.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/voucher/service/VoucherCampaignPublishedListener.kt#L28-L33)
- **Actor / Recipient**: Actor = `ADMIN` publishing a voucher campaign (`AdminVoucherService`); Intended Recipients = all active `CUSTOMER` accounts.
- **Preconditions**: Any admin publishes a voucher campaign triggering `VoucherCampaignPublished`.
- **Root Cause**:
  ```kotlin
  @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
  fun onCampaignPublished(event: VoucherCampaignPublished) {
      val customerIds = jdbc.queryForList(
          "SELECT id FROM users WHERE role = 'CUSTOMER' AND active = TRUE",
          Long::class.java,
      )
  ```
  No `users` table exists in PostgreSQL (`V1..V42` store customers in `customers(id, status, deleted_at)`). Moreover, the query is **not wrapped in `try/catch`** (unlike the inner `notifications.send` loop on `L43-57`).
- **Expected vs Actual**:
  - Expected: Active customers (`SELECT id FROM customers WHERE status = 'ACTIVE' AND deleted_at IS NULL`) receive `VOUCHER_CAMPAIGN_PUBLISHED` notifications; any notification error is caught and logged.
  - Actual: Throws `BadSqlGrammarException: ERROR: relation "users" does not exist` on every campaign publish — **0 customers ever receive campaign notifications**, and the uncaught `AFTER_COMMIT` exception returns `500 Internal Server Error` to the admin *after* the campaign has already committed to PostgreSQL (causing duplicate-retry confusion).
- **Reproduction Scenario**: Admin calls `POST /api/admin/vouchers` to publish a campaign → main TX commits campaign → `AFTER_COMMIT` listener runs `SELECT id FROM users ...` → PostgreSQL throws `relation "users" does not exist` → HTTP 500 returned while campaign exists in DB.
- **Recommended Fix & Regression Test**: Query `SELECT id FROM customers WHERE status = 'ACTIVE' AND deleted_at IS NULL` (batched/paginated + async), wrap the entire `AFTER_COMMIT` listener in `try/catch`, and add a PostgreSQL integration test publishing a campaign and verifying `notifications` rows are inserted without exception.

## 4. Device Tokens, Payment Notifications (`F-006`), Ordering & Multi-Replica Notes

- **Device Token Lifecycle (`DeviceTokenService.kt:16-93`, `FcmChannel.kt:57-69`)**:
  - Supports multiple devices per user (`installationId`), deduplicates by `installationId` and `fcmToken`, reassigns token ownership on shared device login, removes on logout (`unregister(userId, role, installationId)`), deletes all on account deletion (`AccountDeletionService`), and auto-purges `MessagingErrorCode.UNREGISTERED` tokens on FCM send.
  - Hardening notes: `registerOrUpdate` lacks `ON CONFLICT` upsert (concurrent app-start registrations can hit unique constraint `500`), and reassigning solely by client-supplied `installationId` allows overwriting another user's installation row if `installationId` is guessable.
- **Recipient Ownership & PII**: `NotificationHistoryService` and `NotificationService` strictly scope queries by `recipient_customer_id = actor.id` or `recipient_driver_id = actor.id` and deny `ADMIN` (`403`). Zero CCCD/GPLX/bank PII in notification payloads.
- **Payment Notification (`F-006`)**: Confirmed `PaymentService#onRideCompleted` mutates `WALLET → CASH` on shortfall without publishing `PaymentUpdated`, leaving driver/customer unaware of cash collection requirement (already tracked as `F-006`).
- **Ordering, Duplication & Multi-Replica**:
  - `NotificationDispatcher` checks `offer.expiresAt > System.currentTimeMillis()` (`L83`) to drop stale offers before sending.
  - `SimpleBrokerMessageHandler` is in-memory per JVM: in multi-replica deployments, `StompChannel` only sees sessions on the local node (`WS_ONLY` drops cross-node; `WS_THEN_PUSH`/`PUSH_ALSO` fall back to FCM). Clients reconcile authoritative state via REST endpoints on reconnect/resume.
