## 1. End-to-End Payment & Settlement Architecture

```text
[1] BOOKING (POST /api/customer/rides — RideService#createRide)
    - Validates method in {CASH, WALLET} (VNPAY/MOMO rejected -> 400)
    - Computes payableFare = (quote.estimatedFare - discountAmount).coerceAtLeast(0).roundToNearestThousandVnd() [CEILING to 1,000 VND]
    - If WALLET: wallets.checkBooking(customerId, payableFare) [checks balance under FOR UPDATE, does NOT hold funds]
    - Consumes voucher & holds promo_budget (VoucherService#consume -> PromoBudgetService#hold)

[2] ACCEPTANCE (RideStateMachine#tryAssignDriver / adminAssignDriver)
    - wallets.requireEligibleDriver(driverId, cashPayable if CASH else null, rawFare)
      -> Requires CREDIT >= 50,000 VND; if CASH, also requires CREDIT >= commission(cashPayable, rawFare)

[3] RIDE COMPLETION & ATOMIC SETTLEMENT (POST /api/driver/rides/{id}/complete)
    Single ACID DB Tx (RideStateMachine#transition -> BEFORE_COMMIT MANDATORY PaymentService#onRideCompleted):
      1. RideStateMachine locks rides(id), checks VEHICLE_RETURNED + confirmed DROPOFF handover, sets COMPLETED + finalFare
      2. Releases driver BUSY -> statusAfterRide(ONLINE/OFFLINE)
      3. Publishes RideCompleted -> BEFORE_COMMIT PaymentService#onRideCompleted:
         a. Re-locks rides(id), verifies status==COMPLETED, customerId, driverId, finalFare, method in {CASH, WALLET}
         b. Idempotency guard: INSERT INTO ride_wallet_settlements(ride_id) ON CONFLICT DO NOTHING (if 0 -> return)
         c. promoBudget?.spend(ride.id) [!] (F-002 variant checked — see Section 4)
         d. WalletService#settle(rideId, customerId, driverId, finalFare, method, rawFare=ride.fareEstimate):
            - CASH: CREDIT -= fee (may go negative -> driver.status=BLOCKED); if driverNet > fare -> CASH += (driverNet - fare)
            - WALLET (balance >= fare): CUSTOMER -= fare; CASH += driverNet; returns WALLET
            - WALLET (balance < fare): AUTO-FALLBACK TO CASH [OBS-01 / F-005 / F-006] -> CREDIT -= fee; subsidy if driverNet > fare; returns CASH
         e. Updates ride.paymentMethod = settledMethod if changed
         f. UPSERT payments (status = PAID if WALLET or finalFare==0 else PENDING)
      -> Any exception rolls back rides, ride_wallet_settlements, promo_budget, wallets, wallet_transactions, payments together.

[4A] CASH CONFIRMATION (POST /api/driver/rides/{rideId}/payment/cash/confirm — ROLE_DRIVER)
    DB Tx: FOR UPDATE rides(id) -> FOR UPDATE payments(rideId) -> requires COMPLETED, method==CASH
      -> UPDATE payments SET status='PAID', paid_at=now WHERE status='PENDING' AND method='CASH'
      -> Idempotent if already PAID; publishes PaymentUpdated AFTER_COMMIT (first transition only)

[4B] POST-COMPLETION METHOD SWITCH (PUT /api/customer/rides/{rideId}/payment/method — ROLE_CUSTOMER, Idempotency-Key)
    DB Tx: FOR UPDATE rides(id) -> FOR UPDATE payments(rideId) -> checks payment_method_changes(rideId, customerId, key)
      -> Requires COMPLETED + payment.status==PENDING + expectedMethod match (NO voucher allowed_payment_method check [!] F-005)
      -> CASH -> WALLET (WalletService#pendingCashToWallet): rejects if TRIP_EARNING (subsidy) already exists;
         CUSTOMER -= fare, CREDIT += fee (REFUND), CASH += (fare - fee) (RIDE_PAYMENT), payments -> WALLET/PAID
      -> WALLET/PENDING (legacy only) -> CASH (WalletService#pendingWalletToCash): CREDIT -= fee, payments -> CASH/PENDING
      -> Inserts payment_method_changes, updates ride.paymentMethod, publishes PaymentUpdated AFTER_COMMIT
```

- **Formulas**:
  - `finalFare = ceil_1000(max(0, rawFare - discountAmount))` (`MoneyRounding.kt:14-20`, `RideStateMachine.kt:160`)

## 3. Analysis of `OBS-01` (`WALLET → CASH` Fallback — `PRODUCT_DECISION_REQUIRED`)

- **Contradiction**:
  - `docs/WALLET_MODULE.md:22` & `docs/PAYMENT_AUDIT_2026-11-08.md:30`: explicitly specify that if the customer's `WALLET` balance is insufficient at completion, the **entire completion transaction must roll back** (`INSUFFICIENT_CUSTOMER_BALANCE`) and the ride must NOT be marked `COMPLETED`.
  - `WalletService.kt:131-147`, `WalletServiceTests.kt:55-69`, `WalletPostgresTests.kt:154-173`: explicitly implement and test **automatic fallback to `PaymentMethod.CASH`** (charging driver's `CREDIT` wallet and marking `payments` as `CASH/PENDING`).
- **Assessment**: The code/tests reflect a deliberate post-08/11/2026 behavior change to prevent trapping drivers at dropoff when a customer drains their wallet mid-ride, while `docs/WALLET_MODULE.md` was not updated. However, fallback also creates operational & product risks (pushing driver `CREDIT` negative/`BLOCKED` on a ride accepted as `WALLET` without credit-commission pre-check, bypassing `WALLET`-only vouchers [`F-005`], and not notifying either party [`F-006`]).
- **Status**: **`PRODUCT_DECISION_REQUIRED`** — Product owner must confirm whether `WALLET` shortfall at completion should (a) keep `CASH` fallback (then update `docs/WALLET_MODULE.md` and fix `F-005`/`F-006`) or (b) revert to rollback/hold-at-booking per `docs/WALLET_MODULE.md`.

## 4. Concurrency, Transaction Boundaries, Failure Recovery & `F-002` Variant Check

| Scenario | Locks / Constraints / Mechanism | Verdict |
|---|---|---|
| **Complete vs Payment Settlement** | Single ACID tx (`BEFORE_COMMIT`, `Propagation.MANDATORY`); `ride_wallet_settlements(ride_id PK)` + `uq_wallet_trip_earning_ride` + `uq_wallet_customer_ride_type` prevent double settlement. Rollback reverts ride + wallets + ledger + promo + payment atomically. | Protected |
| **Cancel vs Payment** | Both lock `rides(id)` (`FOR UPDATE`) and use `compareAndSetStatus` (`@Version`). `COMPLETE` only allowed from `VEHICLE_RETURNED`; `CANCEL` disallowed from `COMPLETED`. Mutually exclusive. | Protected |
| **Method Switch vs Cash Confirm** | Both lock `rides(id)` then `payments(ride_id)` (`FOR UPDATE`) in identical order. Conditional `WHERE status='PENDING' AND method='CASH'` guarantees single winner (`WalletPostgresTests.kt:241`). | Protected |
| **Concurrent Wallet Debit / Balance Update** | `WalletService#locked` acquires `drivers/customers FOR UPDATE` then `wallets FOR UPDATE` (`PESSIMISTIC_WRITE`), `lock_timeout=3s` → `503 WALLET_BUSY`. DB `CHECK(balance >= 0 OR wallet_type = 'CREDIT')`. | Protected |
| **Crash / Timeout / Retry** | `confirmCashReceived`: idempotent when `PAID`. `PaymentMethodService#change`: idempotent via `payment_method_changes(ride_id, customer_id, request_key)`. `onRideCompleted`: idempotent via `ride_wallet_settlements`. `PaymentUpdated` notification is `AFTER_COMMIT` `REQUIRES_NEW` (best-effort; delivery failure never rolls back money). | Protected |
| **`F-002` Variant Check** | In `PaymentService#onRideCompleted:145`, `promoBudget?.spend(ride.id)` runs inside `ride_wallet_settlements` guard (safe against normal retry). The only path that triggers `RELEASE + SPEND` is `F-002` (`adminAssignDriver` reviving `NO_DRIVER_FOUND`). Note: `PaymentMethodService.kt:42-43` (`pendingWalletToCash`, unreachable for normal rides) inserts `ride_wallet_settlements` without `promoBudget.spend` or voucher subsidy. | Deduplicated with `F-002` |

## 5. New Confirmed Findings (Task 1.13)

### `F-005` — Payment-Method-Restricted Vouchers (`allowed_payment_method`) Bypassed by Both Method Switch and `WALLET → CASH` Fallback
- **Category**: Business Logic / Promotion & Payment Integrity
- **Task ID**: `1.13` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/payment/service/PaymentMethodService.kt:18-55` & `src/main/kotlin/com/nhom15/datxebackend/payment/service/WalletService.kt:128-147`
- **Actor / Entrypoint**: `CUSTOMER` via `PUT /api/customer/rides/{rideId}/payment/method` (`CustomerPaymentController#change`), or `DRIVER` completing a `WALLET` ride with insufficient customer balance (`POST /api/driver/rides/{id}/complete`)
- **Preconditions**: A voucher has `allowed_payment_method = 'CASH'` (or `'WALLET'`) enforced at booking (`VoucherService.kt:198-205, 263-266`).
- **Expected Behavior** *(source: `VoucherService.kt:197-205, 263-266`)*: A voucher restricted to `CASH` must not be redeemable on a `WALLET`-settled ride, and a voucher restricted to `WALLET` must not be redeemable on a `CASH`-settled ride.
- **Actual Behavior**:
  1. **Via `CASH → WALLET` switch**: Customer books with `paymentMethod = CASH` and a `CASH`-only voucher (discount `<= 20%` so no `TRIP_EARNING` subsidy is created). After completion, customer calls `PUT /api/customer/rides/{id}/payment/method` (`CASH → WALLET`). `PaymentMethodService#change` never queries `voucher_usages`/`vouchers.allowed_payment_method` and settles the ride via `WALLET` while keeping the `CASH`-only voucher discount.
  2. **Via `WALLET → CASH` fallback**: Customer books with `paymentMethod = WALLET` and a `WALLET`-only voucher, then spends/empties their wallet before completion. `WalletService#settle` (`WalletService.kt:131-147`) falls back to `PaymentMethod.CASH` while keeping the `WALLET`-only voucher discount and still paying out `promo_budget.spend(ride.id)`.
- **Reproduction (Fake Data)**:
  1. Seed voucher `V_WALLET` (`allowed_payment_method = 'WALLET'`, `FIXED 20,000`).
  2. Customer `1` (wallet `100,000`) books Ride `42` (`100,000`, `WALLET`, `V_WALLET` → `payable = 80,000`).
  3. Customer `1` reduces wallet balance below `80,000` (e.g. spends on another ride or top-down in test).
  4. Driver completes Ride `42` → settles as `CASH` (`80,000`) with `V_WALLET` discount applied and `promo_budget` spent.
  5. Mirror case: `V_CASH` (`allowed_payment_method = 'CASH'`, `FIXED 10,000`) booked as `CASH`, completed, then switched to `WALLET` via `PUT /api/customer/rides/42/payment/method` → succeeds (`200 OK`) with `V_CASH` discount retained.
- **Root Cause**: `allowed_payment_method` is validated only at booking (`VoucherService#calculate`/`consume`), never re-checked during post-completion `PaymentMethodService#change` or `WalletService#settle` fallback.
- **Impact / Blast Radius**: Customers can systematically bypass payment-method-targeted promotional campaigns (e.g., wallet-adoption promos redeemed with cash, or cash-only promos redeemed via wallet).
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
- **Minimal Fix**: In `PaymentMethodService#change`, reject method switch with `409` if `voucher_usages JOIN vouchers` has `allowed_payment_method IS NOT NULL AND allowed_payment_method <> targetMethod`. For `WALLET → CASH` fallback, align with product decision on `OBS-01` (either disallow fallback when a `WALLET`-only voucher is attached, or hold funds at booking).
- **Proposed Regression Test**: Postgres test booking with `CASH`-only voucher, completing, and asserting `PaymentMethodService#change(..., WALLET, CASH, ...)` throws `ConflictException`.

### `F-006` — Silent `WALLET → CASH` Fallback at Completion Never Publishes `PaymentUpdated` Notification
- **Category**: Payment State Synchronization / Side Effects
- **Task ID**: `1.13` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/payment/service/PaymentService.kt:149-161`
- **Actor / Entrypoint**: `DRIVER` via `POST /api/driver/rides/{id}/complete` (`RideProgressController#completeRide`)
- **Preconditions**: Ride `42` was booked with `paymentMethod = WALLET`, `finalFare = 100,000`. At completion, customer's `CUSTOMER` wallet balance `< 100,000`.
- **Expected Behavior** *(source: `docs/WALLET_MODULE.md:170`, `PaymentMethodService.kt:53`, `PaymentNotificationListener.kt:14-26`)*: Whenever a ride's payment method changes between `WALLET` and `CASH`, both driver and customer are notified via `PaymentUpdated` so the driver knows whether to collect cash (and the customer knows cash is now due).
- **Actual Behavior**: `PaymentService#onRideCompleted` (`PaymentService.kt:149-150`) silently mutates `ride.paymentMethod = PaymentMethod.CASH` and inserts `payments(method='CASH', status='PENDING')`, **without publishing `PaymentUpdated`**! Meanwhile `RideNotificationListener#notifyRideCompleted` (`RideNotificationListener.kt:119`) only sends `RideCompletedPayload(rideId, finalFare, distanceKm)` (no `paymentMethod`) to Customer, and `RideProgressController#completeRide` returns `RideStatusResponse` (no `paymentMethod`).
- **Reproduction (Fake Data)**:
  1. Seed Ride `42` (`WALLET`, `finalFare = 100,000`, customer wallet `10,000`, driver `CREDIT = 100,000`).
  2. Call `POST /api/driver/rides/42/complete`.
  3. Observe: DB updates `rides.payment_method = 'CASH'`, `payments.status = 'PENDING'`, driver `CREDIT` debited `-20,000`, **zero `PaymentUpdated` events published** to driver or customer.
- **Root Cause**: `PaymentService#onRideCompleted` updates `ride.paymentMethod` when `ride.paymentMethod != settledMethod` but omits `events.publishEvent(PaymentUpdated(...))`.
- **Impact / Blast Radius**: High operational risk of uncollected cash at dropoff: driver believes the ride was `WALLET`-paid and lets the customer leave while the platform has already debited commission from the driver's `CREDIT` wallet (potentially pushing driver `BLOCKED`).
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
- **Minimal Fix**: In `PaymentService#onRideCompleted`, when `originalMethod != settledMethod`, publish `PaymentUpdated(ride.id, ride.customerId, event.driverId, originalMethod, settledMethod, if (paidNow) PaymentStatus.PAID.name else PaymentStatus.PENDING.name, event.finalFare.amount)`.
- **Proposed Regression Test**: Unit/Postgres test verifying `ApplicationEventPublisher.publishEvent(PaymentUpdated(..., WALLET, CASH, PENDING, ...))` is invoked when `onRideCompleted` triggers `WALLET → CASH` fallback.
