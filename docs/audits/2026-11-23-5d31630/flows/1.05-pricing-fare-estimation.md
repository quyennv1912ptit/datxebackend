## 1. System Inventory & End-to-End Pricing Data Flow

```text
Customer POST /api/customer/rides/estimate (or POST /api/customer/rides)
  │
  ├─► RideEstimateService#validateEstimate  (coords [-90,90], NO ServiceArea check → F-042)
  │   OR RideCreationValidator#validate     (coords [-85.05112878,85.05112878] + ServiceArea + schedule)
  ├─► RedisRateLimiter (rideQuoteRate: 30/min per customerId)
  ├─► PricingRideQuoteService#requirePricing(vehicleType)   ──► pricing_rules (uq_pricing_rules_active)
  ├─► RideRouteService#resolve(customerId, vehicleId, vehicleType, pickup, dropoff, routeQuoteId)
  │     └─► pg_advisory_xact_lock(key) → route snapshot cache (20m TTL) OR Goong Directions HTTP (F-029!)
  ├─► PricingRideQuoteService#quote(RideQuoteInput(pricingAt = scheduledAt ?: now, route = savedRoute))
  │     └─► baseFare + distanceFare + nightSurcharge + returnFee → max(rawFare, minFare) = estimatedFare
  ├─► VoucherService#calculate(actor, code/id, estimatedFare, paymentMethod) → discountAmount
  ├─► payableFare = (estimatedFare - discountAmount).coerceAtLeast(0).roundToNearestThousandVnd()
  │
  ├─► [Create only] WalletService#checkBooking (if WALLET), RideFactory#create (persists fare_estimate, discount_amount ONLY — no pricing_rule_id/breakdown → F-043),
  │                 VoucherService#consume (PromoBudgetService#hold), RideDispatchOutbox
  │
  └─► [Completion BEFORE_COMMIT] PaymentService#onRideCompleted → WalletService#settle(fare=payableFare, rawFare=fareEstimate)
        ├─► driverNetEarning = rawFare - (rawFare / 5)
        ├─► commission       = max(0, payableFare - driverNetEarning)
        └─► CASH: debit driver CREDIT (-commission); if driverNet > payableFare, credit driver CASH (+subsidy)
            WALLET: debit customer (-payableFare), credit driver CASH (+driverNet); shortfall falls back to CASH (OBS-01)
```

## 2. Pricing Formula, Integer Safety & Per-VND Financial Invariants

Verified from [PricingRideQuoteService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/pricing/service/PricingRideQuoteService.kt#L37-L110), [MoneyRounding.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/common/util/MoneyRounding.kt#L14-L20), and [WalletService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/payment/service/WalletService.kt#L106-L162,L228-L237):

| Component | Exact Formula in Source | Arithmetic / Overflow Guard |
|---|---|---|
| `distanceKm` | `BigDecimal.valueOf(distanceMeters) / 1000`, `scale=3`, `HALF_UP` | Rejects `NaN`/`Infinite`/`< 0` (`ROUTE_UNAVAILABLE`) |
| `estimatedDurationMinutes` | `BigDecimal.valueOf(durationSeconds) / 60`, `scale=0`, `CEILING` | `.longValueExact()` |
| `distanceFare` | `(distanceKm * BigDecimal(perKm)).setScale(0, HALF_UP)` | `.longValueExact()` (no silent overflow) |
| `surchargeBase` | `Math.addExact(baseFare, distanceFare)` | Throws `ArithmeticException` on overflow |
| `nightSurcharge` | If `isNight(pricingAt, rule)`: `(surchargeBase * nightSurchargePercent / 100).setScale(0, HALF_UP)` else `0` | Does **not** apply to `returnFeeForDriver`; `.longValueExact()` |
| `waitingFare` | Always `0L` (`per_minute_waiting` / `free_waiting_minutes` stored in DB, not yet billed) | N/A |
| `rawFare` | `Math.addExact(Math.addExact(surchargeBase, nightSurcharge), returnFeeForDriver)` | Throws `ArithmeticException` on overflow |
| `estimatedFare` | `maxOf(rawFare, minFare)` | `>= 0` (`pricing_rules_amount_check`) |
| `payableFare` | `ceil_1000(max(0, estimatedFare - discountAmount))` (`RoundingMode.CEILING`) | `require(this >= 0)` + `.longValueExact()` |
| `driverNetEarning` | `rawFare - (rawFare / 5)` (integer floor division of 20% commission) | Driver receives any fractional-VND remainder (≤0.8 VND) |
| `commission` | `max(0, payableFare - driverNetEarning)` | Absorbs `CEILING` rounding surplus into platform fee |

### Numeric Verification Table (Boundary Cases)

General settlement conservation invariant across **all** voucher levels (0%..100%), where `commission = max(0, payableFare - driverNetEarning)` and `subsidy = max(0, driverNetEarning - payableFare)` are mutually exclusive:
- `driverNetEarning + commission - subsidy = payableFare` (equivalently `driverNetEarning = payableFare - commission + subsidy`).

| Case | `rawFare` | `discount` | `payableFare` | `driverNet` | `commission` | `subsidy` | Conservation Check (`driverNet + comm - subsidy = payable`) |
|---|---:|---:|---:|---:|---:|---:|---|
| Standard CAR (3.125 km, 20% night, 5k return) | `66,500` | `10,000` | `57,000` | `53,200` | `3,800` | `0` | `53,200 + 3,800 - 0 = 57,000` (exact) |
| Non-divisible-by-5 + CEILING (0% voucher) | `31,253` | `0` | `32,000` | `25,003` | `6,997` | `0` | `25,003 + 6,997 - 0 = 32,000` (exact) |
| Heavy Voucher (`discount > 20%`, 30%) | `100,000` | `30,000` | `70,000` | `80,000` | `0` | `10,000` | `80,000 + 0 - 10,000 = 70,000` (exact; driver gets `70k cash + 10k CASH wallet subsidy`) |
| 100% Voucher (`payableFare = 0`) | `30,000` | `30,000` | `0` | `24,000` | `0` | `24,000` | `24,000 + 0 - 24,000 = 0` (exact; driver gets `0 cash + 24k CASH wallet subsidy`) |
| Exact 20% Voucher | `100,000` | `20,000` | `80,000` | `80,000` | `0` | `0` | `80,000 + 0 - 0 = 80,000` (exact) |

### Timezone & Night Surcharge Boundaries (`Asia/Ho_Chi_Minh`)
- `isNight(at, rule)` converts UTC `Instant` via `at.atZone(ZoneId.of("Asia/Ho_Chi_Minh")).toLocalTime()`.
- Overnight window `[22:00, 05:00)` (`start > end`): `21:59:59.999 VN` → `false`; `22:00:00.000 VN` → `true`; `23:59:59.999 VN` → `true`; `00:00:00.000 VN` → `true`; `04:59:59.999 VN` → `true`; `05:00:00.000 VN` → `false`.
- Same-day window `[01:00, 05:00)` (`start < end`): half-open `!isBefore(start) && isBefore(end)`.
- Scheduled rides pass `pricingAt = request.scheduledAt`, so overnight/next-day scheduled rides correctly evaluate night surcharge at the **scheduled pickup time** in Vietnam time, not booking time.

## 3. Admin Pricing Rules, Concurrency & Estimate-vs-Create Consistency

- **Admin Rule Uniqueness & Concurrency**:
  - `V2__support_motorcycle.sql:77` enforces `CREATE UNIQUE INDEX uq_pricing_rules_active ON pricing_rules (vehicle_type) WHERE active = TRUE`.
  - `PricingRuleService#activateLocked` and `deactivateRule` lock all rows for `vehicleType` via `findAllByVehicleTypeForUpdate(vehicleType)` (`ORDER BY rule.id` → deterministic lock ordering, zero deadlock). `deactivateRule` blocks turning off the last active rule unless `force=true`.
  - **Gap (`F-043`)**: `updateRule` mutates an active rule in-place with no version history or admin audit log, and `rides` stores no `pricing_rule_id` or fare breakdown.
- **Estimate-vs-Create Race (T1/T2) & Snapshot Policy (`OBS-14`)**:
  - `RideRouteService#resolve` caches `SavedRideRoute` (keyed by `SHA-256(customerId|vehicleId|vehicleType|pickup|dropoff)`, 20-min TTL) — **ONLY route geometry/distance/duration**, NOT `pricingRuleId` or fare.
  - `T1` (`estimateRide`) returns `50,000 VND` + `routeQuoteId = Q1`. `T2` (Admin `updateRule`/`activateRule` OR clock crossing `22:00 VN`) commits new tariff. `T1` (`createRide` with `routeQuoteId = Q1`) reuses `Q1`'s route distance but calls `quoteProvider.quote()` against the **new** active rule / `Instant.now()`, silently booking at `60,000 VND`.
  - Marked **`OBS-14` (`PRODUCT_DECISION_REQUIRED`)** since neither source nor docs specify whether booking should reject with `409 PRICE_CHANGED` or continue live re-pricing.
- **Goong HTTP Inside Transaction (`F-029`)**: Already tracked in `1.06` (`RideEstimateService#estimateRide` & `RideService#createRide` hold `@Transactional` + `pg_advisory_xact_lock` + HikariCP connection across synchronous Goong HTTP I/O on cache miss).

## 4. Confirmed Findings (`1.05`) & Open Product Decision

### F-042 (`P3` — `CONFIRMED` *(source)*) — `RideEstimateService#validateEstimate` Omits Service-Area Check & Mercator Latitude Bounds, Allowing Out-of-Area Quotes to Consume Goong Quota
- **ID / Severity / Confidence**: `F-042` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [RideEstimateService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideEstimateService.kt#L34-L79) vs [RideCreationValidator.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideCreationValidator.kt#L18-L43)
- **Affected Flow**: `1.05` (Fare Estimation & Quote Consistency)
- **Preconditions**: `ServiceAreaProperties.enabled == true` (production service-area geofence active) and a customer requests an estimate with pickup/dropoff outside the service area (or latitude in `85.05112879..90.0`).
- **Expected Behavior**: `/api/customer/rides/estimate` applies the same coordinate and `ServiceAreaProperties` geofence validation as `POST /api/customer/rides` before invoking Goong Directions API and returning a quote.
- **Actual Behavior**: `RideEstimateService#validateEstimate` only checks `lat ∈ [-90, 90]` and never checks `ServiceAreaProperties`, so it calls Goong Directions API, persists a `SavedRideRoute` snapshot, and returns a price estimate for unbookable out-of-area rides (which then fail with `OUT_OF_SERVICE_AREA` on booking).
- **Root Cause**: Duplicated coordinate validation in `RideEstimateService#validateEstimate` instead of reusing `RideCreationValidator`'s coordinate and geofence checks.
- **Reproduction Scenario**: Enable `serviceArea` centered on Hanoi (radius 50 km) → Customer calls `POST /api/customer/rides/estimate` for Ho Chi Minh City coordinates → succeeds (consumes Goong API call & returns fare) → Customer calls `POST /api/customer/rides` with that `routeQuoteId` → rejected with `OUT_OF_SERVICE_AREA`.
- **Impact**: Unnecessary paid Goong Directions API consumption and misleading UX (showing a bookable fare quote for unsupported areas).
- **Recommended Fix**: Extract shared coordinate + `ServiceAreaProperties` validation and call it in both `RideEstimateService#estimateRide` and `RideCreationValidator#validate`.
- **Suggested Regression Test**: Unit test with `ServiceAreaProperties(enabled = true, ...)` verifying `RideEstimateService#estimateRide` throws `OUT_OF_SERVICE_AREA` without invoking `RideRouteService`.

### F-043 (`P3` — `CONFIRMED` *(source)*) — In-Place Active Pricing Rule Mutation Without Audit History or `rides.pricing_rule_id` / Fare Breakdown Persistence
- **ID / Severity / Confidence**: `F-043` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [PricingRuleService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/pricing/service/PricingRuleService.kt#L68-L92), [RideFactory.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideFactory.kt#L11-L39), [V2__support_motorcycle.sql](file:///f:/datxebackend/src/main/resources/db/migration/V2__support_motorcycle.sql#L130)
- **Affected Flow**: `1.05` (Admin Pricing Rules & Financial Auditability)
- **Preconditions**: An admin updates an active `PricingRule` via `PUT /api/admin/pricing-rules/{id}` after rides were booked under its previous rates.
- **Expected Behavior**: Either active pricing rules are immutable (requiring create + activate new version with audit log) or rides persist `pricing_rule_id` and fare breakdown (`baseFare`, `distanceFare`, `nightSurcharge`, `returnFee`) so historical fares remain explainable.
- **Actual Behavior**: `PricingRuleService#updateRule` overwrites the active `pricing_rules` row in-place with zero audit log, and `rides` stores only `fare_estimate` and `discount_amount` (the `V2` comment `-- ALTER TABLE rides ADD COLUMN pricing_rule_id` was never applied).
- **Root Cause**: Mutable active rule design without tariff versioning or ride-level fare breakdown snapshot.
- **Reproduction Scenario**: Ride `R` booked at `baseFare=20,000, perKm=10,000` (`fare_estimate=50,000`). Admin edits rule #1 to `baseFare=25,000, perKm=12,000`. Subsequent fare dispute on Ride `R` cannot verify which tariff or night surcharge produced `50,000`.
- **Impact**: Loss of financial auditability and inability to explain/reconstruct historical fare breakdowns during customer/driver disputes.
- **Recommended Fix**: Persist `pricing_rule_id` + JSON/column fare breakdown on `rides`, disallow in-place edits on rules referenced by rides (force clone+activate), and log admin pricing mutations.
- **Suggested Regression Test**: Test verifying `createRide` persists fare breakdown / `pricingRuleId` and `updateRule` records an audit trail (or blocks mutating active rules).

### OBS-14 (`PRODUCT_DECISION_REQUIRED`) — Estimate-to-Booking Price Snapshot vs Live Re-Pricing
- `routeQuoteId` (`SavedRideRoute`) locks only route distance/duration for 20 minutes; `RideService#createRide` always re-quotes live against current `pricing_rules` and `Instant.now()`. Product sign-off is needed on whether to add `expectedPayableFare` / fare snapshot validation (`409 PRICE_CHANGED` if admin edits tariff or clock crosses `night_start` between estimate and booking) or keep silent live re-pricing.
