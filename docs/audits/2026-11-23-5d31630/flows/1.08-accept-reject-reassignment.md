## 1. Flow Step Map & Architecture Trace

```text
[1] OFFER ISSUED (RideDispatchService#dispatchRide)
    Redis Lua OFFER_NEXT (under ride:{id}:tick lease)
      -> driver:{d}:lock = rideId (PX offerTimeout)
      -> ride:{r}:current_offer = d:offerId (PX offerTimeout)
      -> driver:{d}:status = OFFERED, ZREM available_drivers d
      -> ride:{r}:state.{currentDriver, currentOfferId, offerExpiresAt}, ZADD dispatch:timeouts
    DB Tx (DriverSelectionService#recordOfferIfEligible):
      -> FOR UPDATE rides(r), FOR UPDATE drivers(d) -> INSERT ride_dispatch_offers(OFFERED)
    Best-effort FCM/STOMP offer push (REST fallback: GET /api/driver/offers/pending)

[2A] ACCEPT (POST /api/driver/offers/{rideId}/accept — ROLE_DRIVER)
    1. Idempotent replay check: if ride.driverId==d && active && offers.accepted(offerId,r,d,gen) -> 200
    2. Pre-check: ride.status==SEARCHING && durable offer matches (offerId, d, gen)
    3. Redis Lua ACCEPT: verifies state/offerId/lock/current_offer/ZSCORE deadline > now
       -> ride:{r}:state = DRIVER_ASSIGNED, driver:{d}:status = BUSY, driver:{d}:current_ride = r
    4. DB Tx (RideStateMachine#tryAssignDriver):
       -> Native conditional UPDATE rides (status=SEARCHING, search_expires_at>now, EXISTS OFFERED offer)
       -> FOR UPDATE drivers(d): checks ONLINE, mayDriveForRide, credit wallet -> sets driver.status=BUSY
       -> offers.close(offerId, ACCEPTED), conversationService.upsert, history, RideStatusChanged + RideDriverAssigned
       -> AFTER_COMMIT: RideNotificationListener notifies Customer (RideAssignedPayload)
    5. On DB return null or exception: if DB confirms assigned -> 200; else ROLLBACK_ACCEPT + close CANCELLED + schedule next

[2B] REJECT (POST /api/driver/offers/{rideId}/reject — ROLE_DRIVER)
    OfferReleaseService#release(r, d, "rejected", offerId)
      -> Redis Lua RELEASE (requires status==SEARCHING && currentDriver==d && currentOfferId==offerId)
      -> UNCONDITIONAL DB UPDATE ride_dispatch_offers SET status='REJECTED' WHERE offer_id=? AND status='OFFERED' [!]
      -> if (released || closed) outbox.schedule(r)

[2C] EXPIRE (OfferTimeoutTask 1s -> outbox.schedule -> RideDispatchService -> OfferReleaseService#expire)
    DB Tx: FOR UPDATE rides(r) -> if status==SEARCHING:
      -> if Redis state==DRIVER_ASSIGNED (crash window recovery) -> ROLLBACK_ACCEPT
      -> release(r, d, "ignored", offerId) -> notify OfferClosedPayload.expired(r)

[3A] DRIVER CANCEL / DISCONNECT REDISPATCH (RideStateMachine#transition)
    DB Tx: FOR UPDATE rides(r) -> DRIVER_ASSIGNED/DRIVER_ARRIVING + (DRIVER CANCEL or SYSTEM REDISPATCH)
      -> if !scheduledSearchClosed && redispatchCount < maxRedispatch: status=SEARCHING, redispatchCount++, driverId=null
         else: status=NO_DRIVER_FOUND (releases voucher!)
      -> FOR UPDATE drivers(oldDriver) -> status=statusAfterRide(ONLINE/OFFLINE), outbox.schedule(r)
      -> AFTER_COMMIT: DriverReleaseService -> RECONCILE_IDLE(oldDriver, r) + RideNotificationListener

[3B] ADMIN REASSIGNMENT (POST /api/admin/rides/{id}/assign — ROLE_ADMIN)
    DB Tx (AdminRideService#assignDriver -> RideStateMachine#adminAssignDriver):
      -> FOR UPDATE rides(r): allows NO_DRIVER_FOUND, or DRIVER_ASSIGNED/DRIVER_ARRIVING if oldDriver disconnected
      -> FOR UPDATE drivers(sorted ids) -> RESERVE_DRIVER_FOR_ADMIN_ASSIGNMENT in Redis (driver:lock)
      -> oldDriver.status = OFFLINE (in DB); newDriver.status = BUSY; ride.status = DRIVER_ASSIGNED, ride.driverId = newDriver
      -> AFTER_COMMIT: COMMIT_ADMIN_RIDE_ASSIGNMENT Lua [!] + notify newDriver & Customer
```

## 4. Confirmed Findings (Task 1.08)

### `F-001` — Admin Reassignment Lua Script Never Deletes Old Driver's `current_ride` Key, Permanently Blocking Reconnect
- **Category**: Redis/DB State Divergence / Reassignment Bug
- **Task ID**: `1.08` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/admin/service/AdminRideService.kt:236-257, 332-343`
- **Actor / Entrypoint**: `ADMIN` via `POST /api/admin/rides/{id}/assign` (`AdminRideController#assignDriver`)
- **Preconditions**: Ride `R` (e.g. `42`) is `DRIVER_ASSIGNED` or `DRIVER_ARRIVING` with `oldDriverId = 7` (`driver:7:current_ride = "42"` in Redis). Driver `7` heartbeat expires (`driver:alive:7` missing). Admin reassigns ride `42` to `newDriverId = 8` (`8 != 42`).
- **Expected Behavior** *(source: `AdminRideService.kt:159-166, 248-254` & `DriverPresenceService.kt:62-65`)*: After reassignment, `oldDriverId`'s Redis `driver:{oldDriverId}:current_ride` is deleted (when equal to `rideId`) and `available_drivers` removes `newDriverId`, so `oldDriverId` can later reconnect and go `ONLINE`.
- **Actual Behavior**: In `COMMIT_ADMIN_RIDE_ASSIGNMENT`:
  - Line `340`: `if redis.call('GET', KEYS[8]) == ARGV[3] then redis.call('DEL', KEYS[8]) end` — compares `driver:{oldDriverId}:current_ride` (which holds `rideId` = `ARGV[2]`) against `ARGV[3]` (`newDriverId`). Unless `rideId == newDriverId`, this is always false, leaving `driver:{oldDriverId}:current_ride` permanently in Redis (no TTL).
  - Line `338`: `redis.call('ZREM', KEYS[4], ARGV[2])` — removes `rideId` (`ARGV[2]`) instead of `newDriverId` (`ARGV[3]`) from `available_drivers` (mitigated in practice by `RESERVE_DRIVER_FOR_ADMIN_ASSIGNMENT:311` already removing `driverId`).
- **Call Trace**:
  `AdminRideController#assignDriver` → `AdminRideService#assignDriver` (sets `oldDriver.status = OFFLINE` in DB) → `afterCommit` → `finishRedisAssignment` → `COMMIT_ADMIN_RIDE_ASSIGNMENT` (sets `driver:7:status = OFFLINE`, fails to `DEL driver:7:current_ride`).
  Subsequently:
  - `RideDispatchRecoveryTask#recoverLostDispatches` (`RideDispatchRecoveryTask.kt:93-120`) checks `drivers.findByStatus(BUSY)` (skips `OFFLINE`) and Redis statuses in `{"BUSY","ON_TRIP","OFFERED"}` (skips `"OFFLINE"`).
  - `DriverPresenceService#updateAvailability(7, online=true)` (`DriverPresenceService.kt:62-65`) checks `hasKey("driver:7:current_ride")` → `true` → throws `409 Conflict (DRIVER_NOT_AVAILABLE)`.
- **Reproduction (Fake Data)**:
  1. Assign ride `42` to driver `7` (`driver:7:current_ride = "42"`).
  2. Delete `driver:alive:7`.
  3. As `ADMIN`, `POST /api/admin/rides/42/assign` with `{"driverId": 8}`.
  4. Observe Redis: `driver:7:status == "OFFLINE"` and `driver:7:current_ride == "42"` still exists.
  5. Wait for `RideDispatchRecoveryTask` (>10s) — key still exists.
  6. As driver `7`, `PUT /api/driver/availability` (`online=true`) → returns `409 DRIVER_NOT_AVAILABLE` indefinitely.
- **Root Cause**: Off-by-one `ARGV` index error in `COMMIT_ADMIN_RIDE_ASSIGNMENT` (`ARGV[3]` used instead of `ARGV[2]` on line 340, and `ARGV[2]` instead of `ARGV[3]` on line 338).
- **Impact / Blast Radius**: Every driver replaced by an admin due to temporary disconnect is permanently locked out from going online until manual Redis intervention or Redis restart.
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P1` High**
- **Variant Analysis**: Checked all 15 `DefaultRedisScript` definitions across `AdminRideService.kt`, `DispatchScripts.kt`, `LocationService.kt`, and `RedisRateLimiter.kt`; no other Lua script has swapped `KEYS`/`ARGV` indexes.
- **Minimal Fix**: In `COMMIT_ADMIN_RIDE_ASSIGNMENT`, change line 338 to `redis.call('ZREM', KEYS[4], ARGV[3])` and line 340 to `if redis.call('GET', KEYS[8]) == ARGV[2] then redis.call('DEL', KEYS[8]) end`.
- **Proposed Regression Test**: Unit/Lua test executing `COMMIT_ADMIN_RIDE_ASSIGNMENT` with `rideId=42, newDriverId=8, oldDriverId=7` asserting `driver:7:current_ride` is deleted and `available_drivers` removes `8` (and `7`), followed by `DriverPresenceService#updateAvailability(7, true)` succeeding.

### `F-002` — Admin Reassignment of `NO_DRIVER_FOUND` Ride Revives Released Voucher & Corrupts Promo Budget
- **Category**: Business Logic / Financial & Voucher Integrity
- **Task ID**: `1.08` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/ride/service/state/RideStateMachine.kt:165-168, 272-320` & `src/main/kotlin/com/nhom15/datxebackend/voucher/service/PromoBudgetService.kt:359-390`
- **Actor / Entrypoint**: `ADMIN` via `POST /api/admin/rides/{id}/assign` (`AdminRideController#assignDriver`)
- **Preconditions**: Customer `1` creates Ride `42` with a voucher (`discountAmount = 50_000`). Search expires → Ride `42` transitions `SEARCHING → NO_DRIVER_FOUND`.
- **Expected Behavior** *(source: `RideStateMachine.kt:165-168`, `VoucherService.kt:305-325`, `PromoBudgetService.kt:301-390`)*: A single-use voucher can be redeemed at most once (`usage_limit` & `uq_voucher_usages_ride`), and `promo_budget` ledger transitions for a ride are mutually exclusive between `RELEASE` and `SPEND`.
- **Actual Behavior**:
  1. On `SEARCHING → NO_DRIVER_FOUND`, `RideStateMachine.kt:165-168` calls `vouchers.releaseForRide(42)`: deletes `voucher_usages` for ride `42`, decrements `vouchers.usage_count`, and `PromoBudgetService#release(42)` inserts `action='RELEASE'` in `promo_budget_ledger`, decrementing `held_amount` and restoring `issuance_reserved`.
  2. Customer `1` can immediately reuse the voucher on another ride (Ride `43`).
  3. Admin calls `POST /api/admin/rides/42/assign` → `RideStateMachine#adminAssignDriver` transitions `NO_DRIVER_FOUND → DRIVER_ASSIGNED` **without** re-consuming the voucher, checking if it was already used/expired, or clearing `ride.discountAmount`.
  4. When Ride `42` completes, `ride.finalFare` still deducts `ride.discountAmount` (`50_000`), driver receives the voucher subsidy, and `PromoBudgetService#spend(42)` queries only `WHERE ride_id = 42 AND action = 'HOLD'` (ignoring the existing `RELEASE` row) and inserts `action = 'SPEND'` (allowed because `uq_promo_ledger_ride_action` is on `(ride_id, action)`), decrementing `held_amount` a second time and incrementing `spent_amount` without deducting `issuance_reserved`.
- **Reproduction (Fake Data)**:
  1. Customer `1` books Ride `42` (`fareEstimate = 100_000`, single-use voucher `V1` `discountAmount = 50_000`).
  2. Let Ride `42` expire to `NO_DRIVER_FOUND` → `voucher_usages` deleted, `V1.usage_count = 0`, `promo_budget_ledger` has `HOLD` + `RELEASE`.
  3. Customer `1` books and completes Ride `43` using `V1` (voucher now spent once).
  4. Admin assigns Driver `8` to Ride `42` (`POST /api/admin/rides/42/assign`) and Driver `8` completes Ride `42`.
  5. Ride `42` settles with `finalFare = 50_000` (2nd discount on single-use `V1`), driver receives 2nd subsidy, and `promo_budget_ledger` for Ride `42` contains `HOLD`, `RELEASE`, AND `SPEND`.
- **Root Cause**: `adminAssignDriver` breaks terminal-state irreversibility by reviving `NO_DRIVER_FOUND` after terminal cleanup (`vouchers.releaseForRide`) has already executed, and `PromoBudgetService#spend` does not guard against rides already having a `RELEASE` ledger entry.
- **Impact / Blast Radius**: Double voucher redemption, unauthorized promo subsidy payout, and permanent drift in `promo_budget` / `voucher_campaign_budget` accounting whenever an admin assigns a driver to a `NO_DRIVER_FOUND` ride with a voucher.
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P1` High**
- **Variant Analysis**: Checked `RideTransitionRules.kt` and `RideStateMachine.kt` — `adminAssignDriver` is the only transition in the entire codebase that transitions out of a terminal `RideStatus`.
- **Minimal Fix**: Either (a) re-validate and re-consume the voucher/promo hold atomically inside `adminAssignDriver` (or clear `ride.discountAmount = 0` / reject if voucher unavailable — requires product decision on UX), AND (b) guard `PromoBudgetService#spend(rideId)` with `NOT EXISTS (SELECT 1 FROM promo_budget_ledger WHERE ride_id = ? AND action = 'RELEASE')`.
- **Proposed Regression Test**: Postgres integration test: book ride with single-use voucher → transition to `NO_DRIVER_FOUND` → verify voucher released → attempt `adminAssignDriver` → assert voucher is either re-held cleanly (preventing reuse) or discount cleared, and `promo_budget_ledger` never has both `RELEASE` and `SPEND` for the same ride.

### `F-003` — Concurrent `reject` Overwrites Durable Offer to `REJECTED` While `accept` Commits `DRIVER_ASSIGNED`
- **Category**: Concurrency / Race Condition & Idempotency Breakage
- **Task ID**: `1.08` | **SHA**: `5d316306e7fe07514e295b6b5fcb5ff9725c257a`
- **Location**: `src/main/kotlin/com/nhom15/datxebackend/matching/service/OfferReleaseService.kt:28-36` & `src/main/kotlin/com/nhom15/datxebackend/ride/service/state/RideStateMachine.kt:231-245`
- **Actor / Entrypoint**: `DRIVER` via `POST /api/driver/offers/{rideId}/accept` racing `POST /api/driver/offers/{rideId}/reject`
- **Preconditions**: Driver `7` holds an active `OFFERED` offer (`offerId = "offer-1"`) for Ride `42`.
- **Expected Behavior** *(source: `OfferReleaseService.kt:33` comment & `RideAcceptanceService.kt:52-54`)*: Once `accept` wins, a late/concurrent `reject` must not mutate the durable offer row, and retrying `accept` with `"offer-1"` must remain idempotent (`200 OK`).
- **Actual Behavior**:
  - **Interleaving**:
    1. `T1` (`accept`): `DispatchScripts.ACCEPT` succeeds in Redis (`ride:42:state = DRIVER_ASSIGNED`).
    2. `T1`: enters `RideStateMachine#tryAssignDriver` → `assignDriverIfSearching` updates `rides` to `DRIVER_ASSIGNED` (`updatedRows = 1`) and locks `drivers(7)`.
    3. `T2` (`reject` with same `offerId`): calls `OfferReleaseService#release` (`OfferReleaseService.kt:28-35`). `DispatchScripts.RELEASE` returns `0` because Redis is already `DRIVER_ASSIGNED`.
    4. `T2`: **still executes line 34** `offers.close(offerId, "REJECTED", 7, 42)` outside any ride lock and without checking `rides.status = 'SEARCHING'`. Because `T1` has not yet reached line 244, the `ride_dispatch_offers` row is still `OFFERED` → `T2` updates it to `REJECTED` and commits immediately!
    5. `T1`: executes `dispatchOffers.outstanding(42)` at `RideStateMachine.kt:244` → returns `null`, and commits `rides.status = DRIVER_ASSIGNED, driver_id = 7`.
  - **Result**: Database ends in an inconsistent state (`rides.status = DRIVER_ASSIGNED, driver_id = 7` while `ride_dispatch_offers.status = REJECTED`). If `T1`'s HTTP response drops and driver retries `POST /api/driver/offers/42/accept` with `"offer-1"`, `RideAcceptanceService.kt:53` calls `offers.accepted(...)` → returns `false` → `409 OFFER_EXPIRED` despite driver `7` owning the ride!
- **Root Cause**: `OfferReleaseService#release` updates `ride_dispatch_offers` unconditionally without acquiring `rides.findByIdForUpdate` or checking `rides.status = 'SEARCHING'` (unlike `OfferReleaseService#expire` which properly locks `rides` first).
- **Impact / Blast Radius**: Corrupts durable offer audit ledger (`REJECTED` for an assigned ride) and breaks idempotent `accept` retry under accept/reject race.
- **Confidence**: High | **Verdict**: `CONFIRMED` (**source-confirmed**) | **Severity**: **`P2` Medium**
