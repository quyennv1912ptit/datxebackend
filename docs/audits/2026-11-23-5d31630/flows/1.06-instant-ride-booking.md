## 1. End-to-End Instant Booking Trace (`POST /api/customer/rides`)

1. **Auth & Role**: `FirebaseAuthFilter` + `RideService#requireCustomer` (`Role.CUSTOMER`).
2. **Customer Serialization Lock**: `customerRepository.findByIdForUpdate(actor.id)` ([RideService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideService.kt#L63-L65)). *(Note: does not check `deletedAt`/`status` after locking — tracked in **`F-024`**, which also affects booking vs concurrent admin ban).*
3. **Idempotency Replay**: `RideCreateIdempotencyRepository#find(actor.id, key)` (5-min TTL, `(customer_id, idempotency_key)` scope). Mismatched SHA-256 `requestHash` → `409 Conflict`; matching key returns existing `CreateRideResponse` without re-creating ride, voucher usage, promo hold, or outbox job.
4. **Input & Active-Ride Validation**:
   - `RideCreationValidator#validate`: finite coordinates (`lat ∈ [-85.05112878, 85.05112878]`, `lng ∈ [-180, 180]`), within Hanoi 50 km service-area circle, non-blank addresses `<= 255`, `note <= 500`, `scheduledAt == null` for `INSTANT`.
   - `ACTIVE_RIDE_STATUSES` check (`L87-L90`): blocks a second instant ride (`409 ACTIVE_RIDE_EXISTS`), while allowing an instant ride when the customer only has a future `SCHEDULED (PENDING)` ride (`ScheduledRideScheduler` defers dispatch if an instant ride is active).
5. **Vehicle Ownership & Capability Snapshot**: `JdbcCustomerVehicleQueryAdapter#findOwnedVehicle` verifies `id = ? AND customer_id = ? AND archived_at IS NULL`, valid `Transmission`/`VehicleType`, rejects `OUTSIDE_MVP`.
6. **Payment Method & Rate Limit**: Rejects anything outside `{CASH, WALLET}`; Redis rate limit `30 req/min` per customer.
7. **Route Resolution & Quote Consistency**:
   - `PricingRideQuoteService#requirePricing` verifies active pricing rule for `vehicleType`.
   - `RideRouteService#resolve` acquires `pg_advisory_xact_lock` on route fingerprint, validates `routeQuoteId` (20-min TTL, `409` on expired/mismatched quote), or calls `GoongDirectionsClient#findRoute` **inside the open `@Transactional` block** (**`F-029`**). Rejects `distanceMeters <= 0` or `durationSeconds <= 0` (`ROUTE_UNAVAILABLE`), which also blocks identical pickup/dropoff coordinates.
   - `PricingRideQuoteService#quote` recomputes fare server-side (`Math.addExact`, `BigDecimal` rounding, night surcharge in `Asia/Ho_Chi_Minh`, `maxOf(rawFare, minFare)`). `CreateRideRequest` has no client-supplied fare field.
8. **Voucher, Promo Budget & Wallet Check**:
   - `VoucherService#calculate` re-validates eligibility, expiry, vehicle/payment constraints, and campaign budget.
   - `payableFare = (estimatedFare - discountAmount).coerceAtLeast(0).roundToNearestThousandVnd()`.
   - If `WALLET`: `wallets.checkBooking(actor.id, payableFare)` verifies sufficient balance (no debit yet; debit occurs at `COMPLETED`).
9. **Atomic Persistence (`PENDING → SEARCHING` + Outbox)**:
   - `rideRepository.saveAndFlush(RideFactory.create(...))` → `idempotencyRepository.insert(...)` → `voucherService.consume(...)` (locks voucher/campaign/promo budget, inserts `voucher_usages` & `promo_budget_ledger(HOLD)`) → `stateMachine.recordCreated(...)` → `startSearching(pendingRide)` (`PENDING → SEARCHING` + `dispatchOutbox.schedule(ride.id)`).
   - All in **one PostgreSQL transaction**: any failure (Goong timeout, voucher exhaustion, wallet shortfall, DB constraint) rolls back completely — zero orphan rides, voucher usages, promo holds, or outbox jobs.

## 2. Confirmed Finding (`1.06`)

### F-029 (`P2` — `CONFIRMED` *(source)*) — `RideService#createRide` and `RideEstimateService#estimateRide` Hold `@Transactional`, `customers FOR UPDATE` & HikariCP Connections Across Synchronous Goong HTTP I/O
- **Location**: [RideService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideService.kt#L58-L107); [RideEstimateService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideEstimateService.kt#L29-L55); [RideRouteService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/routing/service/RideRouteService.kt#L20-L33); [GoongDirectionsClient.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/routing/client/GoongDirectionsClient.kt#L22-L59); [application.properties](file:///f:/datxebackend/src/main/resources/application.properties#L17), [#L88](file:///f:/datxebackend/src/main/resources/application.properties#L88)
- **Root Cause**:
  1. `RideService#createRide` (`@Transactional`) acquires `customerRepository.findByIdForUpdate(actor.id)` (`L63`) and `RideRouteRepository#lock` (`pg_advisory_xact_lock`, `L23`), then synchronously invokes `GoongDirectionsClient#findRoute(...)` on cache miss or omitted `routeQuoteId` while holding both locks and a HikariCP connection.
  2. `RideEstimateService#estimateRide` (`@Transactional`) similarly holds a HikariCP connection and `pg_advisory_xact_lock` across synchronous Goong HTTP I/O.
- **Impact**:
  - With `maximum-pool-size=10` and `lock_timeout='3s'`, a Goong latency spike or timeout across just 10 concurrent estimate/booking requests exhausts the **entire HikariCP connection pool**, stalling all unrelated API traffic, and causes concurrent operations on the same customer (`AdminCustomerService#updateStatus`, `VehicleService`, `WalletService`, `ScheduledRideScheduler`) to fail with 3s `lock_timeout`.
- **Recommended Fix**:
  - Resolve/fetch external Goong routes **outside** the PostgreSQL transaction (short-TX cache check → HTTP call without DB connection/locks → short-TX cache upsert + booking TX), matching the Stage A/B/C pattern used in `DriverVerificationWorkflowService#extractSlot`.

## 3. Concurrency, Partial Failure & Recovery Matrix

| Scenario | Mechanism & Behavior | Verdict |
|---|---|---|
| Two concurrent `createRide` / double tap (with or without `Idempotency-Key`) | Serialized by `customers FOR UPDATE`; with key returns same ride (`409` on hash mismatch); without key second fails `409 ACTIVE_RIDE_EXISTS`. | **SAFE** |
| Retry after client timeout post-commit | With `Idempotency-Key` (within 5m TTL): returns existing ride cleanly. Without key: rejected `409 ACTIVE_RIDE_EXISTS` with `rideId`. | **SAFE** |
| Booking vs Vehicle Deletion (`VehicleService#delete`) | Both acquire `customers(actor.id) FOR UPDATE` (`lockGarage` in `JdbcVehicleRepository#archive`). Strictly serialized. | **SAFE** |
| Booking vs Account Deletion / Admin Ban | `RideService#createRide` locks `customers FOR UPDATE` but never checks `deletedAt == null && status == ACTIVE` (already logged as **`F-024`**). | **Covered by `F-024`** |
| Quote vs Booking price/voucher/budget change | Pricing rule, voucher validity, promo budget, and `WALLET` balance are all re-evaluated fresh inside `createRide`; expired `routeQuoteId` (>20m) returns `409`. *(Note: no `expectedPayableFare` tolerance parameter if admin updates pricing rule mid-quote).* | **SAFE** |
| DB commits, Redis down / outbox worker not yet run / worker restart | `ride_dispatch_outbox` persisted atomically in DB; `RideDispatchOutboxWorker` claims with `FOR UPDATE SKIP LOCKED` (60s lease) & retries (`rescanDelay=3s`, up to `maxTickFailures` → `FAILED_SYSTEM`/`NO_DRIVER_FOUND`); `RideDispatchRecoveryTask` recovers stuck `PENDING` (>30s) & `SEARCHING` rides. | **SAFE** |
| Variants of `F-002`, `F-005`, `F-009`, `F-010`, `F-012`, `F-023`, `F-024` | Verified no new distinct root causes on booking path. | **No duplicates** |
