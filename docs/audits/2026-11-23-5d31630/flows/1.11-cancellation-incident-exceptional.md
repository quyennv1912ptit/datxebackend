## 3. `NO_DRIVER_FOUND` & `FAILED_SYSTEM` Analysis

- **`NO_DRIVER_FOUND`**: Entered only when `now >= searchExpiresAt` (or `retryDispatch` exhausts `maxRedispatch` / `scheduledSearchClosed`). Releases voucher & promo budget (`L165-168`). Can transition to `CANCELLED` (via `RideStatusTransitions.kt:27`) or be revived to `DRIVER_ASSIGNED` by `AdminRideService#assignDriver` (**`F-002`** — double voucher & promo budget corruption). `RideDispatchRecoveryTask` only scans `PENDING`, `SEARCHING`, and `assigned` (`ACTIVE_RIDE_STATUSES`) — never re-dispatches `NO_DRIVER_FOUND`.
- **`FAILED_SYSTEM`**: Entered only via `RideDispatchOutboxWorker#endFailedSearch` when `failures + 1 >= maxTickFailures` while `now < searchExpiresAt`. Releases voucher & promo budget, closes offers, cleans Redis. Cannot be revived by `adminAssignDriver` or any scheduler (`dispatchService.dispatchRide` returns `null` on non-`SEARCHING` and closes outbox job).

## 5. Confirmed Finding (`1.11`)

### F-028 (`P3` — `CONFIRMED` *(source)*) — `TicketService#validateMessage` Bypasses `CloudinaryAssetService`, Allowing External Cloudinary Clouds & Path-Traversal Evidence URLs
- **Location**: [TicketService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/support/ticket/TicketService.kt#L187-L206); compare [CloudinaryAssetService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/uploads/CloudinaryAssetService.kt#L43-L81)
- **Root Cause**:
  Unlike `SupportService#create` (`L29`) and `HandoverCorrectionService#request` (`L36`), which validate evidence URLs through `CloudinaryAssetService#validateCustomerImage` (verifying `cloudName`, `/image/upload/v{n}/`, absence of `..`, query, and fragment), `TicketService#validateMessage` performs an ad-hoc check:
  ```kotlin
  if (uri?.scheme != "https" || uri.host != "res.cloudinary.com") ...
  val folder = "/app_dat_xe/${actor.role.name.lowercase()}/${actor.id}/"
  if (uri.path?.contains(folder) != true) ...
  ```
- **Impact**:
  Any authenticated customer or driver can attach images hosted on an **attacker-controlled Cloudinary cloud** (`https://res.cloudinary.com/<attacker-cloud>/image/upload/v1/app_dat_xe/customer/<id>/spoof.png`) or reference another user's asset via `..` path traversal (`.../app_dat_xe/customer/<id>/../<victim>/img.png`) in incident/support ticket threads, undermining evidence provenance and tenant isolation.
- **Recommended Fix**:
  Validate `TicketService` message images through `CloudinaryAssetService#validateOwnedImage` (or accept `(imageUrl, publicId)` and enforce `cloudName` + normalized path prefix without `..`).
