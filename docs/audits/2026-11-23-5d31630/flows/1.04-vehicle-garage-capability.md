## 2. Customer Garage, Ownership, Concurrency & Historical Integrity

- **Ownership & Security**: `@PreAuthorize("hasRole('CUSTOMER')")` + `requireCustomer(actor)` + every SQL query scopes `WHERE id = ? AND customer_id = ? AND archived_at IS NULL`. `ownerId` is derived strictly from `@CurrentUser actor.id` (no mass assignment). `JdbcCustomerVehicleQueryAdapter#findOwnedVehicle` filters `archived_at IS NULL` and rejects `OUTSIDE_MVP` specs.
- **Concurrency & Locking (T1/T2)**:
  - `JdbcVehicleRepository` (`create`, `setDefault`, `archive`, `updateByIdAndOwnerId`) acquires `SELECT id FROM customers WHERE id = ? FOR UPDATE` (`lockGarage`) — the **exact same lock** acquired by `RideService#createRide` (`customerRepository.findByIdForUpdate(actor.id)`).
  - *Delete vehicle vs Booking*: Serialized on `customers FOR UPDATE`. If `archive` commits first, `createRide` gets `404 VEHICLE_NOT_FOUND`; if `createRide` commits first, `RideFactory#create` snapshots `vehicle_booking_snapshot` (immutable via `V37` trigger `rides_immutable_vehicle_snapshot`), `license_plate`, `vehicle_type`, and `transmission`.
  - *Update vehicle vs Active/Historical Ride*: `fk_rides_vehicle_type` blocks changing `vehicle_type` on any vehicle referenced by a ride (`409 ConflictException`); plate/color edits never mutate historical `rides.vehicle_booking_snapshot` or pricing/settlement.
  - *Scheduled Ride with Archived Vehicle*: Safe — `ScheduledRideScheduler` and `mayDriveForRide` read only the immutable `ride` snapshot, never re-querying `vehicles`.
  - *Account Deletion (`F-024`)*: `AccountDeletionService#deleteCustomer` anonymizes `vehicles` and deletes `vehicle_images` (missing `customers FOR UPDATE` already tracked in `F-024`).
- **Database Integrity (`V37`)**:
  - `chk_garage_active_default CHECK (archived_at IS NULL OR NOT is_default)`
  - `vehicles_plate_number_key ON vehicles (plate_number) WHERE archived_at IS NULL` (archived plates are released cleanly)
  - `uq_garage_owner_default ON vehicles (customer_id) WHERE is_default`

## 4. Confirmed Findings (`1.04`)

### F-044 (`P2` — `CONFIRMED` *(source)*) — `DriverCapabilityService#update` Transitions `ONLINE` Drivers to `OFFLINE` Without Clearing Redis Presence, Evicting `AuthenticatedUserCache`, or Guarding Pending Offers / `BUSY` Rides
- **ID / Severity / Confidence**: `F-044` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [DriverCapabilityController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/driver/verification/DriverCapabilityController.kt#L63-L88)
- **Affected Flow**: `1.04` (Driver Capability Toggle & Online Presence Sync)
- **Preconditions**: An `ONLINE` driver (or `ONLINE` driver with a pending dispatch offer, or `BUSY` driver before `START_TRIP`) calls `PUT /api/driver/capabilities/{groupId}/preference` with `enabled = false`.
- **Expected Behavior**:
  1. When disabling a capability forces `driver.status = OFFLINE` and `onlineVehicleType = null`, the service must also evict `AuthenticatedUserCache` and call `locationService.removeDriver(driverId)` after commit (matching `DriverPresenceService#updateAvailability`).
  2. Disabling a capability should be rejected (`409 DRIVER_NOT_AVAILABLE`) while the driver holds a pending offer (`driver:lock`) or is `BUSY` on an active ride requiring that capability group.
- **Actual Behavior**:
  ```kotlin
  if (driver.status == DriverStatus.ONLINE && driver.onlineVehicleType !in result.acceptingVehicleTypes) {
      driver.status = DriverStatus.OFFLINE
      driver.onlineVehicleType = null
      drivers.save(driver)
  }
  ```
  - Never calls `locationService.removeDriver(driverId)` → leaves stale `driver:{id}:status = ONLINE`, `drivers:geo`, and `available_drivers` in Redis until TTL/cleanup.
  - Never evicts `AuthenticatedUserCache` → `/api/auth/me` serves stale `ONLINE` + `onlineVehicleType` for up to 3s.
  - Never checks `driver:lock` (pending offer) or `driver.status == BUSY` → a `BUSY` driver disabling their active ride's group before `START_TRIP` causes `START_TRIP` to fail with `409 DRIVER_NOT_VERIFIED` (`DriverVerificationEligibility.kt:70,78`).
- **Root Cause**: `DriverCapabilityService` mutates `drivers.status` / `onlineVehicleType` directly via `DriverRepository` without coordinating Redis presence, auth cache, or active-offer/active-ride guards.
- **Reproduction Scenario**: Driver goes `ONLINE` with `CAR` → disables last `CAR` capability via `PUT /api/driver/capabilities/car-auto/preference` (`enabled=false`) → DB becomes `OFFLINE`, but Redis `drivers:geo` and `available_drivers` still advertise the driver as `ONLINE` on `/api/location/customer/nearby-drivers` and during dispatch candidate scans.
- **Impact**: Ghost offline drivers on customer maps, wasted dispatch candidate lookups/offer failures, stale auth cache, and self-bricking `START_TRIP` on `BUSY` rides.
- **Recommended Fix**: Reject capability disable (`409`) when `driver.status == BUSY` or `driver:lock` exists; when transitioning `ONLINE → OFFLINE`, register `afterCommit` hooks to evict `AuthenticatedUserCache` and call `locationService.removeDriver(driverId)`.
- **Suggested Regression Test**: Integration test verifying disabling the last capability for `onlineVehicleType` removes the driver from Redis `drivers:geo`/`available_drivers`, evicts auth cache, and returns `409` while `BUSY` or holding an active offer.

### F-045 (`P3` — `CONFIRMED` *(source)*) — Soft-Archiving Customer Vehicles Leaves Orphaned `vehicle_images` Rows and Unreachable Cloudinary Assets
- **ID / Severity / Confidence**: `F-045` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [VehicleService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/vehicle/service/VehicleService.kt#L41-L44), [JdbcVehicleRepository.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/vehicle/repository/JdbcVehicleRepository.kt#L114-L125, L199-L218)
- **Affected Flow**: `1.04` (Customer Garage Soft-Delete & Media Hygiene)
- **Preconditions**: Customer uploads 1–5 vehicle photos (`POST /api/customer/vehicles/{id}/images`) and later deletes the vehicle (`DELETE /api/customer/vehicles/{id}`).
- **Expected Behavior**: Archiving a vehicle deletes its `vehicle_images` rows and schedules `cloudinaryAssetService.deleteAfterCommit(publicId)` for each image (consistent with `VehicleService#deleteImage` and `AccountDeletionService#deleteCustomer`).
- **Actual Behavior**: `JdbcVehicleRepository#archive` only sets `archived_at = now(), is_default = false` on `vehicles`. `vehicle_images` rows and Cloudinary images remain orphaned permanently, and `deleteImage` (`L204`) requires `archived_at IS NULL`, making them unreachable to the user unless they delete their entire account.
- **Root Cause**: Missing `vehicle_images` cleanup and `deleteAfterCommit` call in `VehicleService#delete` / `JdbcVehicleRepository#archive`.
- **Reproduction Scenario**: Customer adds vehicle V with 5 images → calls `DELETE /api/customer/vehicles/{V}` → all 5 `vehicle_images` rows and Cloudinary assets remain indefinitely.
- **Impact**: Permanent Cloudinary storage leakage and retained customer vehicle photos after explicit deletion.
- **Recommended Fix**: Return deleted `cloudinary_public_id`s from `archive()` (deleting `vehicle_images WHERE vehicle_id = ?`) and invoke `cloudinaryAssetService.deleteAfterCommit` for each.
- **Suggested Regression Test**: Test verifying `VehicleService#delete` removes `vehicle_images` rows and triggers `cloudinaryAssetService.deleteAfterCommit` for each associated `publicId`.

## 5. Review of `1.05` Pricing Invariant (Requirement #15)

Verified directly against [WalletService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/payment/service/WalletService.kt#L106-L162,L228-L237):
- Exact source definitions:
  - `driverNetEarning = rawFare - (rawFare / 5)`
  - `commission = max(0, payableFare - driverNetEarning)`
  - `subsidy = max(0, driverNetEarning - payableFare)` *(credited to driver `CASH` wallet on `CASH` settlement when `driverNet > payableFare`)*
- **General Exact Invariant (All Voucher Levels 0%..100%)**:
  $$driverNetEarning + commission - subsidy = payableFare$$
  - **0% voucher** (`rawFare = 31,253`, `payableFare = 32,000`): `25,003 + 6,997 - 0 = 32,000` (exact; `commission > 0`, `subsidy = 0`).
  - **20% voucher** (`rawFare = 100,000`, `payableFare = 80,000`): `80,000 + 0 - 0 = 80,000` (exact; `commission = 0`, `subsidy = 0`).
  - **30% voucher** (`rawFare = 100,000`, `payableFare = 70,000`): `80,000 + 0 - 10,000 = 70,000` (exact; `commission = 0`, `subsidy = 10,000` credited to driver `CASH` wallet).
  - **100% voucher** (`rawFare = 30,000`, `payableFare = 0`): `24,000 + 0 - 24,000 = 0` (exact; `commission = 0`, `subsidy = 24,000` credited to driver `CASH` wallet).
- **Documentation Correction Applied**: Added this explicit general invariant to [1.05-pricing-fare-estimation.md](file:///f:/datxebackend/docs/audits/2026-11-23-5d31630/flows/1.05-pricing-fare-estimation.md) (no code defect; ledger entries in `WalletService#settle` are exact).
