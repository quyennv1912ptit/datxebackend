## 1. Account Lifecycle Map

| Stage | Endpoint / Entrypoint | Service & Guard Behavior |
|---|---|---|
| **Register (Customer / Driver)** | `POST /api/auth/customer/register`, `POST /api/auth/driver/register` | Rate-limited (`60/min` on `remoteAddr` — **`F-026`**). Verifies Firebase ID token with `checkRevoked = true` (`AuthService#verifyToken`). Enforces admin UID exclusivity (`ensureUidAvailableFor`), requires `phone_number` claim matching request, checks duplicate `firebase_uid` and `phone_number`, inserts `Customer` (`ACTIVE`) or `Driver` (`OFFLINE`, `PENDING`). Customer and Driver **may share the same Firebase UID**. |
| **Login (Customer / Driver / Admin)** | `POST /api/auth/{customer,driver,admin}/login` | Calls `firebaseAuth.verifyIdToken(token, true)`. Customer & Driver fall back to `attachCustomerByPhone` / `attachDriverByPhone` if UID changed for same verified phone (**`F-025`**). Customer blocks `deletedAt != null || status != ACTIVE`; Admin blocks `status != ACTIVE`; Driver checks only `deletedAt != null` (**`OBS-11`**). |
| **Session Auth (HTTP)** | `FirebaseAuthFilter` (`OncePerRequestFilter`) | Calls `firebaseAuth.verifyIdToken(idToken)` **without** `checkRevoked = true` (**`F-016`**). Resolves `roleHint` from `X-Role` header or URI prefix, calls `AuthService#findAuthenticatedUser` (cached 3s when `roleHint != null`). |
| **Session Auth (STOMP)** | `StompAuthInterceptor` + `FirebaseAuthTokenVerifier` | Validates `CONNECT` via `firebaseAuth.verifyIdToken(token)` without `checkRevoked = true` and never re-checks revocation/account status on subsequent frames (**`F-016`**). `ADMIN` rejected on STOMP (`null`). `SEND` destination unrestricted (**`F-014`**). |
| **Profile & Logout** | `GET /api/auth/me`, `POST /api/auth/logout` | `/me` returns cached `AuthUser` fields (`fullName`, `status`, `verificationStatus`, `onlineVehicleType`). `/logout` unregisters device token by `installationId` (does **not** revoke Firebase refresh tokens). |
| **Lock / Unlock (Admin)** | `PATCH /api/admin/customers/{id}/status` (`AdminCustomerService#updateStatus`) | Locks `customers FOR UPDATE`, transitions `ACTIVE`/`INACTIVE`/`BANNED`, cancels `PENDING`/`SEARCHING` rides on `BANNED`, evicts `AuthenticatedUserCache` and calls `firebaseAuth.revokeRefreshTokens` after commit. **No admin lock/unlock endpoint exists for Drivers** (`AdminDriverService` only has `forceOffline`, **`F-004`**). |
| **Delete Account (Self-Service)** | `DELETE /api/auth/account` (`AccountDeletionService#deleteAccount`) | Refuses `ADMIN` (`403`). Soft-deletes & anonymizes `customers` or `drivers`, tombstones `firebase_uid` (and `phone_number` for drivers), deletes device tokens/notifications/skills, anonymizes customer vehicle plates, evicts `AuthenticatedUserCache` after commit, and enqueues `account_cleanup_outbox` for `AccountCleanupOutboxWorker` (Firebase `deleteUser`, Cloudinary asset deletion, Redis presence wipe). See **`F-018`**, **`F-023`**, **`F-024`**, **`OBS-12`**. |
| **Re-registration** | `POST /api/auth/{customer,driver}/register` | Succeeds in `customers`/`drivers` because old row's `firebase_uid` (and driver `phone_number`) was tombstoned — **but** re-registered drivers are permanently blocked at eKYC approval by `F-018`/`F-017` because old `driver_verification_applications` remains `APPROVED` with `locked_cccd_id`/`cccd_id_hmac`. |

## 3. Confirmed Findings (`1.01`)

### F-023 (`P1` — `CONFIRMED`, source) — Deleting One Role of a Dual-Role Account Destroys the Shared Firebase Identity for the Active Sibling Role
- **Location**: [AccountDeletionService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountDeletionService.kt#L90-L95), [#L132-L137](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountDeletionService.kt#L132-L137); [AccountCleanupOutboxWorker.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountCleanupOutboxWorker.kt#L25), [#L38-L44](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountCleanupOutboxWorker.kt#L38-L44); [AuthService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AuthService.kt#L222-L225)
- **Root Cause**:
  `AuthService#ensureUidAvailableFor` explicitly allows a single `firebaseUid` to own both a `CUSTOMER` profile and a `DRIVER` profile. However, `AccountDeletionService#deleteCustomer` and `deleteDriver` unconditionally enqueue `firebaseUid` into `account_cleanup_outbox`, and `AccountCleanupOutboxWorker` unconditionally executes `firebaseAuth.deleteUser(task.firebaseUid)` without checking whether the sibling profile (`drivers` or `customers`) is still active (`deleted_at IS NULL`) under that same `firebase_uid`.
- **Impact**:
  A dual-role user who deletes only their `CUSTOMER` profile immediately has their shared Firebase account deleted — locking out their still-active `DRIVER` profile (even while on an active ride, holding wallet balance, or awaiting a withdrawal), and vice versa.
- **Recommended Fix**:
  Only enqueue Firebase user deletion (`deleteFirebaseUser = true` flag in outbox) when **no other active profile** (`customers`, `drivers`, or `admins` with `deleted_at IS NULL`) references `firebaseUid`; otherwise only clean up role-specific assets/Redis keys and keep the Firebase identity intact.

### F-024 (`P1` — `CONFIRMED`, source) — `AccountDeletionService` Lacks `FOR UPDATE` Lock (Races Against Booking/Assignment) & Nulls Driver Bank Account While Pending Withdrawals Exist
- **Location**: [AccountDeletionService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountDeletionService.kt#L49-L55), [#L99-L105](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountDeletionService.kt#L99-L105), [#L116](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AccountDeletionService.kt#L116); [RideService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/ride/service/RideService.kt#L63-L66)
- **Root Cause**:
  1. `deleteCustomer` (`L49`) and `deleteDriver` (`L99`) load the entity via plain `findById` instead of `findByIdForUpdate`, whereas `RideService#createRide` (`L63`), `RideStateMachine#tryAssignDriver` (`L235`), `adminAssignDriver` (`L290`), and `WithdrawalService#create` (`L31`) serialize on `findByIdForUpdate`. Moreover, `RideService#createRide` (`L63-L66`) does **not** verify `customer.deletedAt == null && customer.status == UserStatus.ACTIVE` after locking `customers`.
  2. `deleteDriver` (`L116`) clears `driver.bankAccountNumber = null` without checking for `PENDING` rows in `withdrawal_requests` (compounding `F-007`).
- **Concrete Interleaving (T1/T2)**:
  - **T1 (`deleteCustomer`)**: `findById(10)` (no lock) → `existsByCustomerIdAndStatusNotIn(10, terminal)` = `false`.
  - **T2 (`createRide`)**: `findByIdForUpdate(10)` acquires lock → inserts `rides(customer_id=10, status=SEARCHING)` → commits.
  - **T1 (`deleteCustomer`)**: tombstones `customers(10)`, wipes vehicle `plate_number` and `rides.license_plate`, enqueues Firebase user deletion → commits.
  - **Result**: An active ride proceeds for a deleted/anonymized customer (or, symmetrically in `deleteDriver` vs `acceptOffer`/`adminAssignDriver`, an active ride is assigned to a deleted driver whose Redis `current_ride`/`lock` and Firebase account are wiped by `AccountCleanupOutboxWorker`).
- **Recommended Fix**:
  Use `findByIdForUpdate` in `deleteCustomer` and `deleteDriver`; validate `deletedAt == null && status == ACTIVE` inside `RideService#createRide` after locking; block `deleteDriver` when any `withdrawal_requests` row is `PENDING` (and see `OBS-12` for positive wallet balance policy).

### F-025 (`P2` — `CONFIRMED`, source) — `attachDriverByPhone` Changes `drivers.firebase_uid` Without Updating Verification Tables, Demoting Verified Drivers & Triggering Self-Lockout
- **Location**: [AuthService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AuthService.kt#L239-L263)
- **Root Cause**:
  When a driver's Firebase account is recreated with a new UID for the same verified phone number, `attachDriverByPhone` updates `drivers.firebase_uid = newUid` (`L261`) but does **not** update `driver_verification_applications.owner_uid` or `driver_verification_projection.owner_uid` (which remain keyed by `oldUid`). Both `attachCustomerByPhone` (`L247`) and `attachDriverByPhone` (`L260`) also call `authenticatedUserCache.evict` *before* transaction commit rather than `evictAfterCommit`.
- **Impact**:
  - `DriverVerificationEligibility` (`projection.current(driver.firebaseUid)`) immediately returns `null`, demoting the `APPROVED` driver to `PENDING` and stripping all ride capabilities.
  - If the driver attempts to re-verify under `newUid`, `hasDuplicateCccdAcrossAccounts` / `hasDuplicateGplxAcrossAccounts` matches their own `oldUid` row (`owner_uid <> newUid`), permanently blocking approval with non-overridable `DUPLICATE_CCCD_ACROSS_ACCOUNTS` / `DUPLICATE_GPLX_ACROSS_ACCOUNTS`.
- **Recommended Fix**:
  Inside the same transaction in `attachDriverByPhone`, lock and migrate `owner_uid` in `driver_verification_applications` and `driver_verification_projection` (and `driver_verification_upload_attempts`) from `oldUid` to `newUid`, and replace `evict(...)` with `evictAfterCommit(...)`.

### F-026 (`P3` — `CONFIRMED`, source) — Login/Register Rate Limiter Keys on `remoteAddr` Without Forwarded-Header Support Behind Reverse Proxy
- **Location**: [AuthController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/controller/AuthController.kt#L34), [#L43](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/controller/AuthController.kt#L43), [#L52](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/controller/AuthController.kt#L52), [#L61](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/controller/AuthController.kt#L61), [#L70](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/controller/AuthController.kt#L70); [AuthLoginRateLimiter.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/auth/service/AuthLoginRateLimiter.kt#L10-L12); [application.properties](file:///f:/datxebackend/src/main/resources/application.properties)
- **Root Cause**:
  `AuthController` passes `servletRequest.remoteAddr` to `AuthLoginRateLimiter` (`60 req / 1 min`), and `server.forward-headers-strategy` is not configured in any profile (`application*.properties`). Behind the production reverse proxy / Cloudflare tunnel, every client shares the proxy's single `remoteAddr`, enabling trivial global login/register DoS (`429 RATE_LIMITED` for all users).
- **Recommended Fix**:
  Configure `server.forward-headers-strategy=framework` (restricted to trusted proxy IPs) or extract the trusted proxy client IP header (`CF-Connecting-IP` / `X-Forwarded-For` from trusted hop) alongside per-account rate limiting.

### 4.2 Outbox Partial Failure Resilience (`AccountCleanupOutboxWorker`)
- **DB commits, Firebase fails**: Transactional outbox guarantees durable retry (`FOR UPDATE SKIP LOCKED`, 60s lease, backoff `5s..3600s`).
- **Firebase succeeds, DB fails**: Prevented by transactional outbox (Firebase is only called *after* DB commit).
- **Worker crash / duplicate claim**: `uq_account_cleanup_owner` prevents duplicate rows; `deleteUser` ignores `USER_NOT_FOUND`, Cloudinary & Redis deletes are idempotent.

### 4.3 `PRODUCT_DECISION_REQUIRED` Items
- **`OBS-11`**: `AuthService#loginDriver` (`L83`) and `loadAuthenticatedUser` (`L151`) permit `BLOCKED` / `SUSPENDED` drivers to log in and call non-driving APIs (unlike `BANNED`/`INACTIVE` customers), and `AdminDriverService` has no driver lock/unlock endpoint. Requires product sign-off on locked/suspended driver access policy.
- **`OBS-12`**: Policy required for (1) account deletion when `wallet_balance` / `income_balance` / `credit_balance > 0` (block vs auto-refund), (2) regulatory retention of deleted drivers' eKYC documents (`F-018`), and (3) identity reuse / cooldown when a deleted driver re-registers with the same CCCD/GPLX.
