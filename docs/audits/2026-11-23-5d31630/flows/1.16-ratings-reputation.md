## 3. Confirmed Findings (`1.16`)

### F-046 (`P2` — `CONFIRMED` *(source)*) — `RideRatingService#driverReviews` Omits `AND is_hidden = false`, Exposing Admin-Moderated / Hidden Comments on Driver Review Endpoints
- **ID / Severity / Confidence**: `F-046` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [RideRatingService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/rating/service/RideRatingService.kt#L41-L57)
- **Actor / Endpoint**: `CUSTOMER` (`GET /api/customer/rides/{id}/driver-reviews`), `DRIVER` (`GET /api/driver/profile/reviews`)
- **Preconditions**: An `ADMIN` hides an abusive/PII-leaking `CUSTOMER_TO_DRIVER` rating via `PUT /api/admin/ratings/{id}/visibility` (`hidden = true`).
- **Expected Behavior**: Hidden rating comments are excluded (`AND is_hidden = false`) from `recent` review lists (matching `customerReviewsForRide` at `L74` and `received` at `L309`).
- **Actual Behavior**: `driverReviews()` queries `SELECT id, stars, comment, created_at FROM ratings WHERE ratee_id = ? AND direction = 'CUSTOMER_TO_DRIVER' ORDER BY created_at DESC, id DESC LIMIT 10` without `AND is_hidden = false`, serving hidden abusive comments to customers and drivers.
- **Root Cause**: `V28` added `is_hidden` moderation and updated `received()` and `customerReviewsForRide()`, but missed `driverReviews()`.
- **Reproduction Scenario**: Customer posts abusive 1★ review on Driver 7 → Admin sets `hidden = true` via `PUT /api/admin/ratings/{id}/visibility` → Next customer assigned to Driver 7 calls `GET /api/customer/rides/{rideId}/driver-reviews` → receives the hidden abusive comment verbatim in `recent`.
- **Impact**: Completely defeats admin moderation of abusive, defamatory, or PII-containing driver reviews.
- **Recommended Fix**: Add `AND is_hidden = false` to the `recent` query in `driverReviews()` (keeping `average`/`total` aligned with `V28`'s rule that hiding affects visibility, not average aggregation).
- **Suggested Regression Test**: PostgreSQL test verifying `driverReviews()` excludes `is_hidden = true` rows from `recent` while preserving `averageRating`.

### F-047 (`P2` — `CONFIRMED` *(source)*) — `RideRatingService#rate` Sends Push Notifications Synchronously Inside `@Transactional` Before DB Commit
- **ID / Severity / Confidence**: `F-047` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [RideRatingService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/rating/service/RideRatingService.kt#L82,L228-L240)
- **Actor / Endpoint**: `DRIVER` (`POST /api/driver/rides/{id}/rating`)
- **Preconditions**: Driver submits a rating for a completed ride (`DRIVER_TO_CUSTOMER`).
- **Expected Behavior**: Publish a Spring domain event handled by `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` (matching `ChatPushListener`, `TicketNotificationListener`, `RideNotificationListener`) so FCM HTTP I/O never holds a DB transaction/lock and notifications never fire on rollback.
- **Actual Behavior**: `notifications.send(...)` executes synchronously inside `rate()`'s `@Transactional` method before commit, holding the HikariCP connection (pool=10) and `customers` row lock across FCM HTTP I/O, and delivering ghost STOMP/FCM notifications if commit fails.
- **Root Cause**: Direct `NotificationPort#send` call inside `@Transactional` instead of `AFTER_COMMIT` event listener.
- **Reproduction Scenario**: Driver submits rating while FCM latency spikes or outer DB commit fails → connection pool held during FCM timeout; on rollback, customer still received STOMP/FCM alert for a non-existent rating.
- **Impact**: HikariCP connection pool pressure under FCM latency and premature/ghost notifications on transaction rollback.
- **Recommended Fix**: Publish `RideRated` event inside `rate()` and dispatch `RatingReceivedNotificationPayload` in an `@Async` `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` listener.
- **Suggested Regression Test**: Test verifying `NotificationPort#send` is NOT called if `rate()` throws/rolls back before commit.

### F-048 (`P2` — `CONFIRMED` *(source)*) — Concurrent `RideRatingService#rate` Submissions for Same Ratee Overwrite `average_rating` With Stale Aggregate (Lost Update)
- **ID / Severity / Confidence**: `F-048` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [RideRatingService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/rating/service/RideRatingService.kt#L176-L219)
- **Actor / Endpoint**: Any two concurrent `CUSTOMER`s (or `DRIVER`s) rating the same ratee across two different completed rides.
- **Preconditions**: Driver 7 has 0 ratings; Customer A (Ride 101, 5★) and Customer B (Ride 102, 1★) submit concurrently under PostgreSQL `READ COMMITTED`.
- **Expected Behavior**: `drivers.average_rating` converges to `3.0` (`(5 + 1) / 2`).
- **Actual Behavior (T1/T2 Interleaving)**:
  1. `T1` inserts `(ride=101, ratee=7, stars=5)` (uncommitted); `T2` inserts `(ride=102, ratee=7, stars=1)` (uncommitted).
  2. `T1` runs `UPDATE drivers SET average_rating = (SELECT AVG(stars) ...) WHERE id = 7` → locks `drivers(7)`, sees only `T1`'s 5★ (`5.0`), commits.
  3. `T2` runs its `UPDATE` (statement snapshot taken before `T1` committed), blocks on `drivers(7)` until `T1` commits, then writes its pre-commit subquery result `1.0` — permanently overwriting `drivers.average_rating = 1.0` instead of `3.0`!
- **Root Cause**: Missing `SELECT id FROM $targetTable WHERE id = ? FOR UPDATE` before inserting into `ratings` / computing `AVG(stars)`.
- **Impact**: Permanent `average_rating` drift on `drivers`/`customers` (affecting matching score in `DriverSelectionService` and customer-facing driver ratings).
- **Recommended Fix**: Acquire `SELECT id FROM $targetTable WHERE id = ? FOR UPDATE` **before** inserting into `ratings` (or before computing `AVG(stars)` in a separate query after acquiring the row lock).
- **Suggested Regression Test**: 2-thread PostgreSQL concurrency test submitting 5★ and 1★ on two rides for the same driver and asserting `drivers.average_rating == 3.0`.

### F-049 (`P3` — `CONFIRMED` *(source)*) — `RatingReceivedNotificationPayload` Exposes `rideId` Despite Stated Anonymity
- **ID / Severity / Confidence**: `F-049` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [RatingReceivedNotificationPayload.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/notification/dto/RatingReceivedNotificationPayload.kt#L6-L26)
- **Actor / Endpoint**: `CUSTOMER` receiving `RATING_RECEIVED` via STOMP/FCM and `GET /api/notifications`
- **Preconditions**: Driver submits a `DRIVER_TO_CUSTOMER` rating.
- **Expected Behavior**: If driver-to-customer ratings are presented as anonymous (`"Đánh giá ẩn danh"`, with `GET /api/customer/ratings/received` omitting `rideId`/`raterId`), the push notification and `notifications` row should not expose `rideId`.
- **Actual Behavior**: `RatingReceivedNotificationPayload` sets `override val rideId: Long`, persisting `notifications.ride_id` and sending `rideId` in FCM/STOMP payloads — letting the customer immediately map the "anonymous" rating to the exact ride and driver.
- **Root Cause**: `rideId` included on `RatingReceivedNotificationPayload` despite anonymous body copy and anonymized `/ratings/received` DTO.
- **Impact**: De-anonymizes driver-to-customer ratings, risking customer retaliation against drivers.
- **Recommended Fix**: Omit `rideId` (`override val rideId: Long? = null`) on `RatingReceivedNotificationPayload` (or confirm product policy if ride-linked ratings are intended).
- **Suggested Regression Test**: Unit test asserting `RatingReceivedNotificationPayload` serializes without `rideId` and `notifications.ride_id` is `NULL`.
