## 2. Confirmed Findings (`1.21`)

### F-034 (`P3` — `CONFIRMED` *(source)*) — Unthrottled Driver GPS Ingest Executes Redundant PostgreSQL Queries Per Sample (HikariCP Pool Amplification)
- **ID / Severity / Confidence**: `F-034` | **P3** | **High** (`CONFIRMED` *(source)*)
- **Location**: [DriverLocationController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/tracking/controller/DriverLocationController.kt#L24-L28); [CoordinateController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/tracking/websocket/CoordinateController.kt#L19-L28); [DriverLocationIngestService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/tracking/service/DriverLocationIngestService.kt#L24-L38); [LocationService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/tracking/service/LocationService.kt#L84-L106)
- **Root Cause**:
  Neither REST `POST /api/driver/location` nor STOMP `@MessageMapping("/location")` applies per-driver rate limiting, and every accepted sample executes **2 to 4 synchronous PostgreSQL queries**: `rides.findFirstByDriverIdAndStatusInOrderByCreatedAtDesc` is queried **twice** per GPS fix (`LocationService.kt:85` AND `DriverLocationIngestService.kt:29` via `RideTrackingQueryAdapter`), plus `offers.driverHasOffer(driverId)` (`L91`) and `driverRepository.findById(driverId)` (`L104`) on offline/restart recovery.
- **Expected vs Actual**:
  - Expected: Per-driver GPS rate limit (e.g., max 1–2 Hz) and single active-ride lookup (or Redis-cached `current_ride` fast path) so high-frequency GPS streams cannot exhaust PostgreSQL connections.
  - Actual: A buggy or malicious driver client advancing `timestamp` by 1ms within `[now, now+30s]` at 50–100 Hz triggers 100–300 PostgreSQL queries/sec per driver against a 10-connection HikariCP pool (`application.properties:17`), risking pool starvation and customer STOMP fan-out flood.
- **Reproduction Scenario**: Authenticated driver sends 100 consecutive `POST /api/driver/location` or STOMP `/app/location` frames in 1s with monotonically increasing `timestamp` within `+30s` → all 100 pass `SAVE_SAMPLE` and execute 200+ PostgreSQL queries.
- **Recommended Fix & Regression Test**: Enforce a minimum sample interval / per-driver rate limit (e.g., 1s in `SAVE_SAMPLE` Lua or `RedisRateLimiter`) and return the `activeRide` snapshot from `LocationService` to eliminate the duplicate `RideRepository` query; add a unit test verifying burst GPS updates within `< 1s` are throttled.

### F-035 (`P2` — `CONFIRMED` *(source)*) — `GET /api/customer/places/popular` Leaks Individual Customers' Private Dropoff Addresses & Exact Coordinates (No k-Anonymity Threshold)
- **ID / Severity / Confidence**: `F-035` | **P2** | **High** (`CONFIRMED` *(source)*)
- **Location**: [CustomerPlaceService.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/customer/service/CustomerPlaceService.kt#L53-L91); [CustomerPlaceController.kt](file:///f:/datxebackend/src/main/kotlin/com/nhom15/datxebackend/customer/controller/CustomerPlaceController.kt#L38-L47)
- **Root Cause**:
  ```sql
  SELECT dropoff_address, dropoff_lat, dropoff_lng, COUNT(*) AS uses
  FROM rides
  WHERE status = 'COMPLETED'
    AND dropoff_address IS NOT NULL ...
    AND created_at >= NOW() - INTERVAL '180 days'
  GROUP BY dropoff_address, dropoff_lat, dropoff_lng
  ORDER BY uses DESC
  LIMIT 50
  ```
  There is **no `HAVING COUNT(DISTINCT customer_id) >= N`** (k-anonymity threshold) and no exclusion of private residential addresses.
- **Expected vs Actual**:
  - Expected: Only genuinely public/multi-user destinations (visited by at least `N` distinct customers, e.g., `HAVING COUNT(DISTINCT customer_id) >= 5`) appear in `/api/customer/places/popular`.
  - Actual: Any single completed ride's exact dropoff street address and exact `(lat, lng)` (including private homes of individual customers) is returned to **every authenticated customer** calling `GET /api/customer/places/popular`.
- **Reproduction Scenario**: Customer A completes 1 ride to their private home address → Customer B calls `GET /api/customer/places/popular?proximityLat=...&proximityLng=...` → receives Customer A's exact home address and coordinates with `useCount = 1`.
- **Recommended Fix & Regression Test**: Add `HAVING COUNT(DISTINCT customer_id) >= 5` (configurable threshold) and add a PostgreSQL test confirming a single-customer dropoff address is never returned by `popular()`.
